## Verified behavior

The [editor](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/workflow/editor.tsx) uses Liveblocks-backed React Flow storage, shared cursors, undo/redo and a selected-run preview. Fired edges are derived from run results without writing those decorations back into the graph. Users can add/edit nodes and connections, while cycle-producing connections are rejected. The [shared graph definitions](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/workflow/shared.ts) include input, Jev, LLM and output nodes; there are no general filesystem, shell or mailbox-action nodes.

Jev nodes expose choice, ordered score and `noul` probability questions. Choice follows the selected option; score follows a rounded expected level; `noul` follows a configured cutoff, initially 0.7. That rounding is a branching policy, not necessarily the most probable ordinal level. An additional “always” output fires whenever a reached Jev node returns, including an empty-question result. Joining nodes use either any fired incoming handle or all incoming handles. Text from fired parents is joined; conflicting accumulated question IDs are overwritten by later parents. Output nodes collect parent texts into named arrays. These details are visible in the [executor](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/workflow/server/executor.ts).

The [demo graph](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/workflow/demo.ts) triages a support request, drafts a billing or technical reply, creates an escalation note from an AND condition, and checks/revises tone. The [run endpoint](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/api/workflows/%5BworkflowId%5D/runs/route.ts) accepts text up to 20,000 characters and either returns a run ID immediately or waits for the trace. Independent graph branches can execute concurrently. Results record node status, inputs, outputs, fired handles, model identity, duration and whether a mock was used.

## Limits that should shape our experiment

- **Mock execution is a distinct condition.** Missing provider keys select a keyword-based Jev mock or a canned streaming LLM reply. Both [Jev](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/workflow/server/typesafe.ts) and [LLM](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/workflow/server/llm.ts) results carry `mock`. Their apparent confidence cannot establish model quality.
- **Limits are not complete cancellation.** The executor declares 25 node executions and a 60-second timer. It passes the abort signal to LLM streaming but not to `askJev`, whose SDK call has no signal in this implementation. Treat that timer as an intended limit, not a verified wall-clock guarantee.
- **Trace completeness needs its own contract.** The [run types](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/workflow/runs.ts) do not retain a graph revision/hash. The editor overlays results on current stored nodes and edges. Feed-write failures are logged and ignored by execution. Our replay must retain its original graph and disclose incomplete persistence.
- **Hosted collaboration remains demo-scoped.** The [authentication endpoint](https://github.com/CTNicholas/jev-workflow-builder/blob/9a652d22216028a64ccaa7468754e45e1860618b/app/api/liveblocks-auth/route.ts) selects example identities and grants broad example-room writes; the run endpoint does not establish an authenticated caller's workflow permission. Actual tenant authorization, budgets and input-retention policy are prerequisites for our hosted integration. No deployed security behavior was tested.

## Fit with this repository

We already use React Flow in [agent experiments](../experience-prototypes/src/agent-experiments.tsx), and [Model Routing Lab](../roadmap/routing/README.md) supplies typed decisions, eligible destinations, hard restrictions, bounded delegation and outcome records. The missing interaction is editable control flow with a replay that explains why a branch ran and what changed after an edit. Reuse those interfaces and existing Bun/Vercel application; a separate Next.js deployment or a general experiment engine is unnecessary.

The next-wave experiment should answer whether typed branching improves a bounded task enough to justify its extra decisions, latency and cost. A visual path alone is not evidence of task success. Start with authored support requests and exported drafts, distinguish recorded/provider/mock runs, and preserve an immutable graph for each trace. A later Jimothy classifier could fill a node only when its fixed task exactly matches; general task changes remain unsupported. Keep that optional adapter separate from this interaction study.
