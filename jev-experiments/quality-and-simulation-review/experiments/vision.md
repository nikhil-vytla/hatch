# Vision to action

Verdict: redesign. Highest priority: P1. Keep the honest failed caption as the starting example. The experiment needs an evidence-gathering loop with a measurable goal before an action label can demonstrate useful vision-assisted behavior.

## Current boundary and strengths

The published input is a 1200 × 953 screenshot of the gallery, 98,058 bytes. It visibly contains a website headline, navigation, experiment cards and a diagram. The browser-local `Xenova/vit-gpt2-image-captioning` model described it as "a collage of different types of electronic devices." The worker uses Transformers.js 3.8.1, WASM, q8 weights and `max_new_tokens: 60`. It sends the generated text to Jev, not pixels. Source: `web/src/local.worker.ts:60–75`, `web/src/recipes.ts:321–339`. Paths are relative to `jev-experiments`; the relevant source, image and record match frozen main `4c0c40d5`.

The single recorded Jev response chooses describe with probability 0.50, inspect 0.40, ask 0.10 and navigate 0. It scores sufficient evidence at 0.25 and chooses unclear for the broad scene. The record and current UI explicitly acknowledge the caption failure and call this a composition smoke test, not a vision benchmark. That candor is a strength. Source: `results/vision.jsonl`, `experience-prototypes/src/misc.tsx:301–315`. The preparation script copies the real input image, and the audit confirms the published copy has the same SHA-256. Source: `scripts/prepare.ts:94–98`; [original probe and counts](../probes/vision.json).

The archived gallery has image upload, a worker, progress, an 8 MB input limit and cancellation that terminates the worker and aborts the request. Source: `web/src/main.ts:292–420`. The canonical React experience is now a fixed-image caption-repair exercise. Visitors can edit the description and question, then ask Jev for action and sufficiency. It does not rerun local perception. These are distinct interfaces; the earlier browser run is recorded evidence, not something this audit reran.

## Findings

### P1: low evidence does not lead to a concrete inspection step

The record scores evidence at 0.25 yet proposes describe. No code combines those outputs into an abstention or inspection policy. The choices contain no target region, crop, object ID, clarification question or expected result. Neither the worker recipe nor the current component executes an action. Source: `web/src/recipes.ts:324–339`, `src/jev_lab/compositions.py:426–454`, `misc.tsx:343–362`.

This does not prove describe is objectively incorrect: the generic request "What should I inspect next?" has no independent success criterion. It does show that detecting uncertainty does not repair the missing evidence. Replace the label-only task with a concrete objective such as finding a named link in a sandbox screenshot. Jev chooses an evidence request or proposed target from available region IDs; code resolves crops, tracks what was observed and checks whether the goal was reached. A low evidence score should trigger a declared policy learned on development cases, not be treated as calibrated merely because it is numeric. No unsafe action is currently executed.

### P1: a repaired decision retains the old caption and task metadata

The current handler sends `{description: caption, question}` and then stores `{...row, ...r}`. The response contains answers and transport metadata, but no copy of that edited description or question. The stored row therefore keeps the original erroneous caption, original task, local-model name and device beside the new answers. The gateway correctly marks the response live; the defect is the retained input/perception metadata, not the source flag. Source: `misc.tsx:343–357`, `server/gateway.ts:252–265`.

The [offline merge probe](../probes/vision.ts) reproduces this with a clearly synthetic response: the submitted website description and new task are both absent from the resulting row. The probe is a state-update reproduction, not model evidence or a browser test. Edits made during an outstanding request also have no revision/abort guard. Store the exact request, image hash, caption provenance and question version with every result. Keep original and manual captions as separate revisions. New input must mark previous answers stale; late responses remain attached to their original revision.

### P2: the repair comparison changes more than its evidence

The recorded browser recipe sends `local_perception` and `task`, asks three questions and supplies specific action descriptions. The current React handler sends `description` and `question`, asks only action and enough_evidence, and uses bare action names. The Python composition is a third similar prompt. Source: `web/src/recipes.ts:321–339`, `compositions.py:426–445`, `misc.tsx:343–355`. The record does not contain the exact question map, so source inspection reconstructs a likely browser protocol rather than proving its request bytes.

A changed downstream answer would therefore not isolate the effect of a corrected caption. Extract one versioned protocol and run original and repaired text through identical questions, model settings and tasks. Keep the recorded historical response visible as historical evidence. A paired repair experiment should retain both raw responses and any deterministic guard outcome, without choosing a favorable repeat.

### P2: the current interaction cannot gather new visual evidence

The React component has one fixed image, two textareas and a JSON fold. There is no upload, crop, OCR, local worker or visually grounded action overlay. Its image alt text only says that this is the actual input image, which does not describe the screenshot's content. Source: `misc.tsx:291–365`. The manual repair is useful, but it cannot test whether the pipeline can recover from its own caption error or help a visitor inspect an unfamiliar picture.

Reuse the archived worker lifecycle in an explicit local-perception mode. Show original image, numbered crops and exact caption/OCR evidence beside each proposed action. Make manual correction a labeled intervention. Keep a prepared recorded case available if model download fails, and expose download cost, local timing and cancellation. Meaningful alt text and a keyboard-operable region list should provide the same inspection controls as pointer crop selection. Caption text is the only material sent to Jev by default; the UI should show that data flow before live use.

### P2: one result lacks the record needed for attribution and replay

There is one authored image and one task, with no independent target annotation, perception baseline, repaired result or repeated run. The stored latency is 237.3 ms from the gateway output. It excludes download, preprocessing and caption generation. The published row has no image hash, model revision, generation config, caption timing or exact request; `transport` is null. Source: `results/vision.jsonl`, `web/src/recipes.ts:371–380`, `web/src/local.worker.ts:63–74`; probe provenance fields.

The screenshot's caption error is directly inspectable, but no perception error rate, action accuracy or end-to-end speed follows from this one observation. Record per-stage inputs/hashes, pinned weights and runtime, timings and failures. Separate caption quality, evidence sufficiency, chosen target and completed task. Do not use Jev's sufficiency score to grade Jev's action, and do not turn a human correction into automatic perception success.

## Richer simulation: inspect a fictional screen

The visitor receives a screenshot of a fictional dashboard and a goal such as "find where I can change the date range." A split view shows the screenshot, a timeline of evidence and the current proposed target. They can act manually, let Jev request a crop, or hand control back at the same state. A first global caption may omit the control. Jev can ask for one of a fixed set of regions, request OCR there, ask the user to disambiguate two dates, propose a target or abstain. The next observation contains only returned evidence with source, bounding box and uncertainty; it never contains the evaluator's target ID.

Code owns immutable image/evidence revisions, crop coordinates, a finite action menu, tool budgets, timing, the sandbox's state transitions and hidden goal checks. Jev chooses what evidence would help and which observed target fits the user's intent. It does not generate authoritative coordinates from an ungrounded caption. Clicking is simulated inside the fictional dashboard, never on the user's desktop. Success advances to a second screen so a complete task, such as selecting the last seven days and confirming the filter, is measurable.

A checkpoint saves image, task, evidence, tool budget and accepted actions. The visitor can undo and branch between global-caption, OCR and crop-assisted policies. Human takeover remains available while requests are pending. Late responses cannot mutate a new branch. Tool failure retains the current screen and offers manual inspection or a labeled recorded replay. If later animated scenes are added, their world clock runs independently of model latency; a model response names the observation time and expires when its target no longer exists.

Acceptance requires source-linked evidence for every proposed target, no evaluator labels in model input, consistent normalized coordinates after image scaling, cancellation with no late mutation, visible distinction between generated/manual/recorded evidence, keyboard-equivalent crop selection, and a complete independently checked goal. Low-information and missing-target cases must end in a justified clarification or abstention within budget. Report raw action proposals and guarded executed actions separately.

## Evaluation and external coverage

Start with 40 held-out authored screens, three goals per screen and two visual conditions per goal, producing 240 tasks. Include tiny labels, repeated icons, ambiguous references and missing targets; use a separate 20-screen development set for policies. Each test has hidden executable target/transition checks. Compare fixed global captions, global captions plus OCR, adaptive crop/OCR evidence and human-authored complete evidence. The latter is an upper-bound intervention, not an automated perception condition. Add deterministic OCR token matching and a seeded random-region baseline. A direct multimodal model is a separate paid condition only after a declared budget.

For each of three repeats, allow at most three Jev decisions per task per evidence mode. The four modes therefore require at most 8,640 logical evaluations, or 25,920 typed answers if each evaluation returns action, region and sufficiency. Tool calls and local perception passes have separate counts. Cross-case batching can reduce requests, but dependent observation rounds cannot be merged into one call. Freeze caption outputs for a decision-only ablation and rerun perception separately to isolate stage variability. Bootstrap paired outcomes by source screen, not by each correlated crop or repeat. Publish goal completion, unsupported target rate, missing-target abstention, clarification usefulness, localization error, evidence retention, tool count, p50/p95 per-stage and end-to-end latency, download/memory costs and every failure.

For an external grounding check, use the full [ScreenSpot-v2 release](https://huggingface.co/datasets/OS-Copilot/ScreenSpot-v2), pinned at `5efbb1f1b5463a575f2eb7bc30fe29e49c15f93c`. This audit counted the three small official annotation files directly: 334 desktop, 501 mobile and 437 web instructions, totaling 1,272 across 730 unique image filenames. Text/icon counts are 194/140, 290/211 and 234/203 respectively. The hashes and source URLs are in the probe. Current experiment coverage is 0/1,272; metadata inspection is not a benchmark run. The Hub's automatic viewer reports a generation error, so load the declared JSON files rather than interpreting its apparent train split as the evaluation protocol. The release is linked by its authors' [OS-Atlas repository](https://github.com/OS-Copilot/OS-Atlas).

Use the [original ScreenSpot scorer](https://raw.githubusercontent.com/njucckevin/SeeClick/main/pretrain/screenspot_test.py) for point-inside-ground-truth-box accuracy, counting invalid outputs as failures, and report each platform and text/icon subset. Pin the scorer and preserve the v2 annotation revision. Jev can select among image-derived candidate regions and code can emit the selected region's center. This is a proposal-assisted grounding pipeline, not direct pixel grounding by Jev. Report candidate recall separately; do not obtain candidate regions from gold boxes. The full external pass for three text-evidence methods and three repeats is 11,448 logical evaluations with one target choice per case. Batches of 20 independent cases would require 576 physical requests before retries, allowing a partial batch for each method/repeat. A three-step adaptive extension has a separate ceiling of 34,344 evaluations. Images, OCR/caption compute, candidate generation and scorer parity are setup blockers; no images or model weights were downloaded here.

Benchmark screenshots must not be used to tune captions, thresholds or prompts. Repeated instructions on the same image are correlated, and public training exposure remains uncertain. ScreenSpot evaluates localization on a static screenshot; it cannot establish multi-step task completion, uncertainty handling or the complete simulation's play quality.

[Transformers.js 3.8.1](https://huggingface.co/docs/transformers.js/v3.8.1/en/pipelines) already supports the worker-based perception stage and explicit model revisions. Keep that runtime and measure its actual load/inference behavior. [Tesseract.js](https://github.com/naptha/tesseract.js) supplies browser/worker OCR, which is directly relevant to the missed UI text; request region/word output explicitly and retain boxes rather than only concatenated text. Neither makes a caption truthful. Jev's useful role is choosing the next evidence request and interpreting the task against that evidence, which the independent task checks must test.

P1/S: repair result provenance and revision guards. P1/M: define concrete target/evidence actions and an explicit abstention policy. P2/S: unify prompts and retain paired repaired results. P2/M: restore local perception with crop/OCR and full stage records. P2/L: build the sandbox journey and authored evaluation, then run the complete external grounding comparison after a manifest and resource budget. The evidence/crop log can later support diagram inspection or visual search without claiming that text-only Jev sees pixels.
