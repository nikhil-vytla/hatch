# JudgeBench: repair the score, then make order sensitivity tangible

**Verdict: repair. Highest priority: P1.** The current React experience is substantially better than the original gallery: full inputs are present and failed requests were recovered. The main problem is now scientific interpretation. Its 77% accuracy is an ordered-decision measure; applying the official two-order JudgeBench rule to the same evidence gives **63%**.

## Current behavior and strengths

The catalog calls this **JudgeBench** and asks whether position changes correctness (`experience-prototypes/src/catalog.ts:197`). Jev sees one question and two candidate answers, chooses A/B, and separately scores whether A and B are correct. Deterministic code swaps candidates, remaps the dataset winner, derives the atomic winner, and aggregates predictions (`src/jev_lab/benchmarks.py:100–165`). Dataset labels are never sent to Jev.

The published input is `experience-prototypes/results/judge.jsonl`, selected by `experience-prototypes/publication.json:15`, not the older root results. It contains **100 pairs / 200 completed ordered judgments**, including 14 recovered transport failures. Recovery retains completed predictions and the original request hash (`experience-prototypes/scripts/recover.ts:74–120`). Recomputed scores are **77% ordered accuracy**, **71.5% atomic ordered accuracy**, and **28% order disagreement**. Availability is correctly separated from quality in React (`experience-prototypes/src/benchmarks.tsx:269–285`).

All 200 rows contain the full question and both candidate strings. A read-only comparison found **zero discrepancies** against pinned upstream commit `e2c52c284e735e139b3daa61c206ee208f36c461`. The visitor can read both candidates, pick A/B, reveal the dataset/Jev judgments, inspect probabilities and source details, and filter mistakes (`experience-prototypes/src/benchmarks.tsx:118–185,245–258`). These are real recorded judgments, not generated placeholders. No browser interaction was performed for this audit.

## Findings

1. **P1 — The prominent metric is not the official benchmark score.** `src/jev_lab/benchmarks.py:153` and the recovery aggregation at `experience-prototypes/scripts/metrics.py:18` pass all 200 orientations to generic classification. The [official scorer](https://github.com/ScalerLab/JudgeBench/blob/main/utils/metrics.py) reverses the second vote and credits a pair only when its combined vote favors the correct candidate; opposite votes tie. Here, **63 pairs are correct in both orders, 28 disagree, and 9 are wrong in both**. Thus official two-order accuracy is 63%, not 77%. The UI's “accuracy on returned answers” label is literally accurate, but beside the benchmark title it invites an invalid leaderboard comparison. **Fix:** show official two-order score first, keep ordered accuracy as a diagnostic, expose correct/tied/incorrect counts, and match upstream scoring with fixed test vectors including null and tie votes. Report completion separately rather than silently excluding failed pairs.

2. **P1 — The sample is small and changes the benchmark's composition.** `src/jev_lab/data.py:101–120` round-robins source × response-model strata, giving 50 pairs from each model. Official splits are **350 GPT pairs and 270 Claude pairs**, verified in the [dataset card](https://huggingface.co/datasets/ScalerLab/JudgeBench/raw/main/README.md). Coverage is 100/620 = **16.13%**; GPT 14.29%, Claude 18.52%. The sample is **82% MMLU-Pro**, compared with **308/620 = 49.68%** in the complete release. It has only 83 distinct `(source, original_id)` questions; the full release has 268. Repeated pairs and orientations are not independent questions. **Fix:** run both complete splits and report each separately plus a clearly defined pair-weighted aggregate. Cluster uncertainty by source question; preserve the 100-pair run as a named historical sample.

3. **P1 — Order disagreement is counted but cannot be investigated naturally.** The UI navigates 200 rows, so adjacent examples can be the same pair in reverse. There is no paired view, disagreement filter, or canonical identity for the selected answer (`experience-prototypes/src/benchmarks.tsx:25–38,98–116`). Example pair `88c03f19-2b85-5b04-b0f8-42e9a765098e` selects displayed B in both orders: it first selects the correct underlying answer at probability .98, then the wrong underlying answer at .54. **Fix:** navigate unique pairs; make swap a controlled intervention with both recorded outcomes displayed together after the visitor votes. Show canonical answer identity, not only A/B.

4. **P2 — “Atomic” checking is neither independent nor truly atomic.** The two Noul questions ask whole-answer correctness while both answers share the same state; they do not isolate claims or produce evidence (`src/jev_lab/benchmarks.py:124–142`). There are five equal-score cases, deterministically assigned A. Its 71.5% ordered accuracy and **51% official two-order score** trail the pairwise method. **Fix:** label it “whole-answer scoring,” represent equal scores as ties, show it as an ablation, and separately evaluate isolated-answer grading against the shared-state version. A later claim-checking method must attach verifiable claim outcomes, not merely additional Jev confidence values.

5. **P2 — The reader is usable but weak for difficult mathematical/code cases and blind comparison.** Candidate bodies are plain text in 420px scrolling regions (`experience-prototypes/src/style.css:2140`), leaving math/code markup uninterpreted; 17 candidate appearances contain dollar math or code fences. “Mistakes” filtering and searching target letters leaks outcome information before a visitor votes (`experience-prototypes/src/benchmarks.tsx:29–36`). Choosing an answer immediately reveals labels and no session score persists. **Fix:** separate unfiltered blind practice from diagnostic review; provide an expand-reading view, safe Markdown/math rendering, source/pair deep links, saved first votes, and an explicit reveal action. Keep raw text available byte-for-byte. Do not present self-selected visitor results as an unbiased human benchmark.

## Richer interaction: the order-sensitivity courtroom

Start with a blind queue of unique pairs. The visitor reads rendered or raw candidates, records a first choice and confidence, then reveals the independent dataset label and the two recorded Jev judgments. A **Swap seats** control exchanges displayed positions while colored answer identities remain fixed; an outcome strip shows “correct both ways / changed its mind / wrong both ways.” Filters select source family, response model, confidence, or disagreement in diagnostic mode. A compare panel overlays pairwise selection, whole-answer scoring, and a two-order consensus that abstains on disagreement. Export the pair, original text, votes, timestamps, prompt hash, and scoring rule.

State: pair ID, orientation, first human vote, reveal status, selected judge method, and optional new-run state. Jev supplies only the defined judgments; code owns swapping, label isolation, identity remapping, scoring, export, and UI. A new live judgment is explicitly marked exploratory and never overwrites benchmark evidence. Pending, cancellation, malformed response, and provider failure preserve the readable case and mark the new vote unavailable; they cannot reveal or change gold labels.

Acceptance: all 620 pairs readable in both orientations; raw strings identical to pinned source; swapping twice restores text and identity; gold and recorded judgments hidden until reveal; original first vote immutable within a practice attempt; every aggregate matches exported evidence; no UI conflation of 1,240 orientations with 620 independent pairs; both dark/light modes and keyboard navigation retain readable formulas, code, focus and expanded text. Add pure scoring/data-integrity tests and a small browser test of vote → reveal → swap → export. Existing test searches found no JudgeBench-specific scoring or component test.

## Evaluation design and feasibility

- **Official run:** freeze current prompt/schema and model/provider metadata before running all 350 GPT and 270 Claude pairs in both orders: **1,240 requests / 3,720 question decisions** per pass with the existing three-question request. This covers every released pair; no training split or tuning on these labels. Largest cached serialized state is only 9,172 bytes, so payload size is not an evident blocker. Actual tokenizer preflight remains required. Already cached data suffices; no new dataset download or expensive candidate generation is needed.
- **Repeats:** three separately recorded passes, randomized request scheduling with seeds 42/43/44, total **3,720 requests / 11,160 decisions** before retries. Seeds change scheduling, not a claimed Jev sampling control. Resume only transport failures; log retries and model alias resolution. The practical constraint is provider availability, not the earlier arbitrary miniature sample budget.
- **Scoring:** reproduce the official two-order rule exactly, per split and source family; retain ordered accuracy, disagreement, always-correct/both-wrong counts, completion, Brier score, and retry-inclusive latency. Report the new 63% historical-sample score beside the original 77% diagnostic, not as a rerun result. Gold outcomes are upstream objective labels, not a second model's opinion.
- **Baselines/ablations:** fixed displayed-A (0% official two-order score when complete, 50% ordered), independent random votes (25% expected official score, 50% ordered), canonical random answer held constant across swaps (50% expected for both), deterministic longer-answer baseline (**47% on this sample**), current pairwise, and whole-answer scoring. These baselines make the unusually strict two-order score interpretable. Add isolated-answer Noul scoring in two calls per pair, **1,240 extra requests per pass**, explicitly distinct from the existing shared-state method.
- **Uncertainty/confounds:** bootstrap source-question clusters with 10,000 resamples, fixed RNG, retaining both models, candidate pairs and orientations within clusters. Report finite-benchmark score exactly and the interval as uncertainty about broader questions, not incomplete knowledge of these fixed 620 cases. Compare methods with paired cluster intervals; report run-to-run variability separately. Public benchmark contamination and correctness-label limitations cannot be ruled out; no “human-level judge” claim follows. Any rubric tuning uses a separate development corpus, with benchmark labels locked.
- **Success:** complete coverage and reproducible official scoring are required, regardless of whether accuracy improves. Accept an enhanced judging method as better only if its paired question-cluster interval for official-score improvement excludes zero; show the unchanged baseline and all negative results. Consensus abstention must expose coverage and error, not merely inflate accepted-case accuracy. No additional paid baseline is necessary for the first full run.

## Useful libraries and next steps

- [SciPy bootstrap](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html): compute reproducible confidence intervals after preparing source-question cluster statistics. Jev supplies decisions; statistical code supplies uncertainty.
- [react-markdown](https://github.com/remarkjs/react-markdown): render candidate Markdown safely without enabling raw HTML. Its documented math-plugin route can make formulas readable; preserve a raw-text toggle and avoid executing candidate code. Jev remains the judge, not the renderer.

**P1/S:** add upstream-compatible scoring, pair/group IDs, baseline checks and the corrected historical report. **P1/M:** complete both official splits with resumable immutable evidence and question-cluster analysis. **P1/M:** build unique-pair navigation, swap comparison and disagreement review. **P2/M:** add isolated-answer/consensus ablations and safe rich reading. This work can later support reward-label quality audits and agent-verifier consistency without importing benchmark correctness claims into those domains.
