# JevFrame: an inspectable review table

Research only, checked 2026-09-21. No package was installed, tests executed, inference requested or experiment implemented. Source review supports the facts below; the experiment and evaluation are proposals.

## Verified upstream facts

[JevFrame](https://github.com/ktaletsk/jevframe) is authored and maintained by **Konstantin Taletskiy**. The inspected `main` revision is [`16bd3eae69b71284a75747fb4bf199b14ba1b075`](https://github.com/ktaletsk/jevframe/commit/16bd3eae69b71284a75747fb4bf199b14ba1b075), committed on 2026-09-21. Its package metadata declares version `0.1.0`, alpha status, Python 3.10+, and `typesafe-sdk>=0.7,<0.8`; pandas and Polars are optional integrations. Its MIT license names Taletskiy and requires retaining the copyright and permission notice when copying substantial code. The license covers this library, not a blanket license for models or datasets. Sources: [package metadata](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/pyproject.toml), [license](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/LICENSE).

The Python accessors expose `noul`, `choice`, `score` and multi-question `evaluate`. They return pandas or eager Polars values. The engine calls the official asynchronous TypeSafe client once per uncached distinct row context, with every requested question in that call. Its default concurrency is 16 workers. It is a hosted-inference DataFrame integration, not a local model or a browser runtime; it accepts an official SDK client rather than an arbitrary decision adapter. Sources: [engine](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/src/jevframe/_engine.py), [pandas integration](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/src/jevframe/pandas.py), [Polars integration](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/src/jevframe/polars.py).

| Concern | Source behavior and consequence |
| --- | --- |
| Row identity | Results are assigned by input position. pandas indexes, including duplicates, are copied; indexes are not implicitly model context. Filtering first changes the positional frame used by reported failures. A persistent experiment row ID is still needed for exports and reruns. |
| Missing or invalid input | Selected columns or a synchronous callable construct JSON context. Null handling is explicit. Context-construction errors always raise, even with `errors="coerce"`; they can occur after other requests finish. Preflight the entire proposed batch before sending it. See [context conversion](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/src/jevframe/_context.py). |
| Failure | An invalid, incomplete or failed answer makes the entire row fail. Coercion returns missing fields and positional warnings, not a negative prediction. Cancellation drains workers but cannot undo completed remote requests. The [mocked engine tests](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/tests/test_engine.py) cover these behaviors; they do not establish live-provider reliability. |
| Probabilities | Noul returns the yes probability. Choice retains the SDK-selected label and every option probability. SDK `confidence` is a separate field; the wrapper does not establish that it measures calibrated correctness or equals the chosen option's probability. |
| Ordinal score | Score returns the expected zero-based level and its distribution. The displayed level is the distribution's maximum, with first-level tie breaking. It is not generally a probability. Choice permits 1–255 options; Score permits 2–10 levels. Distribution keys and sums are validated with a `1e-6` sum tolerance, without renormalization. See [output validation](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/src/jevframe/_schema.py). |
| Cache and requests | The optional bounded memory cache holds successful complete rows. Within one evaluation, identical in-flight contexts share a request only when caching is enabled. Keys incorporate serialized context/questions, criterion order, model and client configuration/identity; indexes do not. Cache clearing changes a generation counter so old requests cannot refill the cleared cache. There is no disk cache. See [cache](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/src/jevframe/_cache.py). |

The output table drops raw HTTP response information: per-row attempt counts, provider usage and actual execution identity need separate instrumentation. Concurrency is not a bulk model batch, a requests-per-second limit or evidence of a speedup. Polars support is eager; no LazyFrame execution is established. Model aliases may move, so recording `jev-latest` alone is insufficient for repeatability.

The upstream [marimo example](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/examples/reviews.py) already provides editable review questions, probability displays and a request inspector. Its pinned [README](https://github.com/ktaletsk/jevframe/blob/16bd3eae69b71284a75747fb4bf199b14ba1b075/README.md) documents a sponsored gateway with cached defaults and a shared allowance of 2,000 new row requests per UTC day. That gateway shares cached inputs and answers and is intended for public data. The library itself does not silently provide this fallback. Gateway availability, live accuracy, latency and the published wheel's equivalence to the inspected revision were not tested.

## Proposed experiment: Review Table

Add a later, bounded experience for exploring **how a probability threshold changes a review queue**. Start with 50 recorded, attributed public product-review sentences. The first action is **Show uncertain reviews**: it filters the table immediately using saved results. Changing a threshold updates queue size, coverage and reference-label errors without requesting inference. Selecting a row opens its exact submitted context, typed questions, complete distributions, status and execution record. A user can compare three forms of the same sentiment question:

- Boolean: "Does this review express positive sentiment?"
- Choice: negative or positive, with explicit descriptions.
- Score: two ordered levels, negative then positive.

The two-level Score deliberately shares the binary reference labels; its expected level equals its positive probability. This is a check of typed framing, not an ordinal-quality benchmark. More levels or new questions may be editable exploratory inputs, but their outputs have no reference accuracy until a separate labeling protocol exists.

Inputs are the built-in public preset or an explicitly supplied CSV with stable `row_id` and `review` columns. The initial runner should cap submissions at 200 rows and 4,000 UTF-8 bytes per review, reject excess input with row-specific reasons, and send only the selected review text. Keep labels and row IDs out of model context. Freeze the whole input snapshot before running; edits or resets invalidate the displayed run association. No stale completion may replace a newer table.

Export an annotated CSV plus a JSONL decision ledger and a small manifest. Retain row IDs/positions, full distributions, source/model/protocol hashes, cache status, failures and timing boundaries. CSV is a convenience view; JSONL preserves typed values and explicit missing states. Shared URLs reproduce public presets and thresholds only. User text belongs in an explicit local export, never automatically in a URL.

Reuse JevFrame through a pinned Python runner or downloadable notebook that produces these artifacts. The existing Bun application can replay and inspect them. Live web execution needs a separate deployment decision because the current application cannot import Python accessors. Do not reimplement the SDK loop in TypeScript and present that as a JevFrame integration. No new public catalog entry should appear before the recorded example, first action and export work.

## Proposed reproducible evaluation

Freeze the following protocol and actual input hashes before inference. This document does not claim that a corpus manifest or results already exist.

1. **Data and split.** Use the Amazon subset of [UCI Sentiment Labelled Sentences](https://archive.ics.uci.edu/dataset/331/sentiment%2Blabelled%2Bsentences), credited to Dimitrios Kotzias and licensed CC BY 4.0. UCI describes 500 positive and 500 negative sentences per domain and intentionally excludes neutral sentiment. Pin the downloaded archive and selected file hashes. Group identical text after Unicode normalization, case folding and whitespace collapse; exclude groups with contradictory labels and publish counts. Within each class, sort remaining groups by SHA-256 of `jevframe-review-table-v1` plus normalized text, retaining a canonical original row per group. Take 100 per class, first 40 for calibration and remaining 60 for held-out evaluation: 80/120 rows. The visible 50-row preset comes only from calibration. These sampled derivative scores must not be presented as full-dataset benchmark results or real-world complaint prevalence.
2. **Conditions and baselines.** Submit the three frozen questions together for each row, using one recorded model version, a 30-second timeout, zero retries and concurrency 4 for the primary run. Use a calibration-label prior and a keyword rule as semantic baselines. The proposed rule counts case-folded whole-word occurrences of `good, great, excellent, love, perfect, best, happy, recommend` minus `bad, poor, terrible, hate, broken, worst, disappointed, useless`; positive totals predict positive, negative totals negative, and ties follow the calibration majority, choosing positive on a majority tie. It has no negation handling and receives no invented probability-calibration scores. A direct official-SDK loop with identical mocked replies is a separate wrapper-correctness baseline, not a different model. Local-model comparison can follow only through an explicit compatible adapter and separate condition.
3. **Primary metrics.** For the Boolean question, report held-out accuracy at `p >= 0.5`, Brier score, negative log likelihood with a declared numerical epsilon, and a five-bin reliability table. Report requested, valid, failed, skipped and unsupported counts. Show accuracy among valid rows alongside correct/requested coverage-sensitive accuracy; failures never become negative labels. Choose a review threshold from `{0.5, 0.6, 0.7, 0.8, 0.9, 0.95}` on calibration alone by maximum coverage at at least 90% observed retained accuracy. If no threshold qualifies, retain no automatic decisions. Publish held-out risk/coverage and counts without claiming a guaranteed risk bound.
4. **Typed and row behavior.** Treat Choice/Score accuracy, cross-form disagreement and maximum probability deltas as secondary diagnostics. Align probabilities by semantic label before comparing option order. On 12 preselected held-out rows, repeat with reversed row order, reversed Choice options, and each question in a separate request. Distinguish repeated-provider variation from the exact guarantees checked using mocks. Exercise duplicate indexes, MultiIndexes, duplicate contexts, empty tables, null policies, pandas/Polars and columns/struct parity, invalid distributions, partial replies, cancellation and context errors. No row may disappear or acquire another row's answer.
5. **Performance and request budget.** On 24 fixed calibration rows, measure concurrency 1, 4 and 16 with three fresh-cache repetitions, each followed by a same-client warm-cache replay. Disable retries for this bounded live measurement and count transport attempts independently of progress events. The planned live budget is 476 initial requests: 200 primary, 216 performance and 60 robustness. Mock failure tests make no provider calls. Record total wall time including context preparation, queue time where observable, per-attempt network time, rows/second, peak process memory, failures and cache/in-flight reuse separately. Warm cache is reuse latency, not model latency; remote gateway cache state may be unknown. Report measured usage/cost only when provided or verifiably billed, otherwise mark unknown. No speed or savings claim precedes these results.

Probabilities represent this model's outputs, not established calibration. "Uncertain" means a declared review policy, such as `max(p, 1-p) < threshold`; it is not a discovered ground-truth label. Keep SDK confidence separate. Bootstrap intervals may describe sampling variation but cannot establish generalization beyond this small, binary, deliberately balanced review subset. Pretraining overlap is unknown.

## Dependencies and acceptance

Keep this in the next-wave map until the entry experience and bounded evaluation are funded; it need not expand the first-release gate. Root owns ticket names and scheduling.

- Pin the upstream commit and Python dependency lock, retain MIT attribution, and verify wheel/source provenance before choosing a released package. Keep Python dependencies isolated from the Bun application.
- Add a declared mapping to the [shared decision contract](../roadmap/runtime/contract.ts): Noul to false/true probabilities, Choice labels to stable option IDs, and Score indices to explicit ordinal values. Restrict ordinal adapters to the upstream 2–10-level limit; reject unsupported ranges rather than truncating. Preserve SDK confidence and transport evidence in the artifact sidecar. Existing local runtimes are not drop-in JevFrame clients.
- Record model identity and supported context limits, capture sanitized attempt/usage evidence through supported SDK instrumentation, and choose direct BYOK or recorded execution explicitly. Do not use the shared sponsored gateway for user CSVs or controlled performance claims.
- Validate the frozen dataset/splits, artifact hashes and row mappings before the first request. Reuse concrete artifact-loading/cancellation utilities where appropriate, without adding a universal experiment engine. Keep this evaluation separate from the [completed local typed-decision study](../roadmap/training/README.md).
- Acceptance requires provider-free row/failure tests, the actual recorded run and held-out metrics, reproducible CSV/JSONL export, and keyboard, mobile, dark-mode and reduced-motion review of the entry flow. Passing wrapper tests alone does not establish useful model quality. A weak semantic result can remain inspectable and experimental.

This proposal borrows JevFrame's table integration and request-inspection approach with attribution. Its new contribution would be the threshold-driven review queue, reproducible artifacts, matched typed framings and explicit accounting. No new capability or measured benefit is claimed yet.
