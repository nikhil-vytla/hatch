# Cafe Jev notes

- Created the investigation folder before writing implementation files. Read the beverage audit, current adaptive menu, API gateway, recording codec and credentials loader.
- The old drink finder and adaptive questionnaire duplicate eight fixed drinks. Cafe Jev uses a new, versioned fictional ingredient and recipe catalog. The original adaptive questionnaire remains a separate experiment.
- The model gateway returns categorical answers, not arbitrary JSON. The shared contract therefore extracts each preference as an enum and asks for its supporting transcript turn. Evidence is the exact source turn, not a claim that a model-generated quotation proves meaning.
- The simulator's private customer goal is kept outside the public request builder. Code computes recipe legality, stock, prices, hard constraints, soft preference scores and terminal customer satisfaction independently.
- The app supports only the published budget choices. An unrecognized explicit budget becomes an unresolved constraint and requires an exact supported choice before confirmation. It is never rounded upward.
- Live responses carry session and revision tickets. Editing, choosing a recipe, answering, undoing, replaying or changing customers invalidates and aborts pending requests.
- Declared 102 authored requests before running Jev: all 81 partial temperature/caffeine/dairy/sweetness states and 21 customer, negation, soft-preference, contradiction, revision, budget, inventory, ambiguity and conversation cases. These are development fixtures, not the audit's proposed locked 120-customer test.
- Recorded the shared typed contract through the existing local-model gateway. Three-case batches completed at first, then repeatedly hit HTTP 429 with a roughly one-minute Retry-After. Switched to one case per call, retained every failed attempt separately, and added bounded retries that honor long provider delays across gateway deadlines.
- The catalog contains 304 legal recipes. Default stock leaves 228; soy is always sold out, and oat is sold out for seeds divisible by five. Exactly three of the new catalog's 81 core partial preference states have no match. This is a different menu from the original eight-drink experiment, which had 16 no-match partial states.
- Browser QA found an exclusion explanation using the first hot recipe even when a drink family could be made cold. Changed the explanation to use that family's closest recipe, so a caffeine requirement produces a caffeine explanation.
- Applied the Playwright and papercuts skills during browser verification. Vite hot reload invalidated browser element references twice. A fresh snapshot restored them; the papercut CLI confirmed that this repo has not opted into its log, so no log file was created.
- Desktop browser checks verified a size change updates $4.50 to $5.50 and provenance to Your choice; Undo restores $4.50 and Recorded Jev. The sold-out oat customer exposes zero matching recipes, explicit dairy/creaminess relaxations and no confirmation action. Mobile at 390 px has no horizontal overflow, and both light and dark scenes were visually inspected.
- Source-turn evidence preserves the customer's entire relevant utterance. An extraction can still be semantically wrong even when its evidence turn exists. Raw mistakes stay visible and count against annotation accuracy independently from deterministic guard results.
- Finished all 102 declared cases with no missing rows. Exact preference extraction was 89/102, exact feasible sets 93/102, and direct finite-state extraction 77/81. Eight raw family suggestions violated the authored requirements; none of the admitted recipe suggestions did. Of 80 model questions, 65 split the gold feasible set or resolved a conflict. The raw no-match policy found two impossible cases, missed five and incorrectly rejected one feasible case.
- Preserved 24 failed provider batches separately. The 82 completed physical requests and all failed batches used 146 provider attempts. Completed-request median latency was 358 ms, p95 2,844 ms; these numbers exclude the outer retry waiting time and are not end-to-end customer latency.
- Final verification passed 16 tests with 3,066 assertions, including complete evidence coverage and exact replay through the current shared contract. A delayed browser response could not overwrite a newer manual size choice or discard an edited draft.
- Recording batches use named cases and prefixed question ids, while live mode supplies one public transcript. Both use the same typed extraction schema and question builder; the report states this context difference. Original batch boundaries and reconstructed public payloads are committed so the recording method is reviewable.
