
== 1. Growing the gateway in 5 chat turns (each change passes the kernel's gates)
  turn 1 usage        -> accepted rev-0001 (2 functions live)
  turn 2 prices       -> accepted rev-0002 (4 functions live)
  turn 3 quotas       -> accepted rev-0003 (5 functions live)
  turn 4 validation   -> accepted rev-0004 (5 functions live)
  turn 5 top spender  -> accepted rev-0005 (6 functions live)

== 2. Real traffic (every request is a recorded, exactly-once transaction)
  request 1  set gpt price 50c/1k                 -> ok 50
  request 2  set claude price 300c/1k             -> ok 300
  request 3  alice calls gpt, 1200 tok            -> ok 1200
  request 4  bob calls claude, 500 tok            -> ok 500
  request 5  alice calls claude, 300              -> ok 1500
  request 6  alice quota 2500                     -> ok 2500
  request 7  alice calls gpt, 600                 -> ok 2100
  request -- alice calls gpt, 500 (over quota)    -> REFUSED: over quota
  request 8  claude price rises to 1000           -> ok 1000
  request 9  bob calls gpt, 700                   -> ok 1200
  request 10 carol calls claude, 400              -> ok 400
  live top_spender(): "bob"  live cost(alice): 3.9

== 3. Audit: the live code as data (no execution, just reading forms)
  call graph (caller -> callees):
    cost          -> (none)
    record_usage  -> usage
    set_price     -> (none)
    set_quota     -> usage
    top_spender   -> cost
    usage         -> (none)
  can CHANGE state (calls swap-state!, directly or via callees): record_usage, set_price, set_quota
  READ-ONLY functions:                                          cost, top_spender, usage
  depend on the PRICE table (reads "prices", directly or via callees): cost, set_price, top_spender
  depend on QUOTAS: record_usage, set_quota
  billing (cost, top_spender) is read-only; only this price reader also writes: set_price
  throw sites: record_usage: key required/model required/tokens must be a positive whole number/over quota; set_quota: already over that quota
