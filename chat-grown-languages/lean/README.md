# Lean 4 live kernel for chat-grown software

A kernel for the JSON-lines protocol (`../PROTOCOL.md`) written in Lean 4 itself. The process imports `Lean`, keeps a
Lean `Environment` as the live image, elaborates every accepted form in-process and runs it through `evalConst`. The
language-specific layer: a change may carry **Lean theorems** (the protocol's `laws`), and the kernel rejects it if any
proof fails to check, on this change or on any law proved earlier.

Result: `node --experimental-strip-types --no-warnings bench/conformance.ts lean` -> **51/51 checks pass**; start 0.3-0.7 s,
develop avg ~350 ms (45 ms for turn 1, 930 ms for turn 8 with 8 laws re-proved), full run ~8 s.

## Files
`Kernel.lean` (the kernel), `Chat/Prelude.lean` (State, JSON codecs, calling convention), `reference.json` (generated by
`tools/gen_reference.py`: 8 turns with proved laws + 6 probes), `prompt.md`, `showcase/demo.ts` + `showcase/transcript.txt`,
`NOTES.md`, `setup.sh` (lake build), `run.sh`.

## Live kernel: why in-process
Option (a) (elaborate into an `Environment` inside the kernel) worked on the first try and is fast: elaborating a small def is
20-60 ms, no process start or re-import per candidate. `try` and `develop` build the candidate environment from the unchanged
prefix of the live one, so a candidate costs only the forms that changed or depend on a change. Since Lean cannot replace a
constant, "late-bound redefinition" is done by re-elaborating the dependents; a callee whose type changes becomes a static error in its callers.
Trade-off: a call cannot be killed after 1 s; it is reported as a timeout and its thread abandoned.

## Money: Int cents, proofs possible
Everything money-like in the app is an `Int` count of cents; the JSON boundary converts exactly (decimal mantissa/exponent,
round half up like the reference's `Math.round`). Floats would make every law unprovable; with cents `omega` and `simp` close the arithmetic.
The price: the app has no `Float`, sub-cent inputs are quantised, and the user's turn-4 request ("0.1+0.2 shows 0.3") is satisfied by the representation from turn 1.

## Proved laws in the reference (all re-checked on every develop)
`add_expense_count`, `by_category_sums_to_total` (turn 3's law, with a lemma about the association-list insert),
`total_is_exact_sum`, `add_expense_adds_exactly_the_amount`, `add_expense_keeps_state_well_formed` (the scenario's
`expenses-shape` invariant, proved rather than checked), `over_budget_means_over` (turn 6's law), `set_budget_keeps_state_well_formed`,
`top_category_is_a_max` (turn 7's law). Turn 4's "total is whole cents" holds by type; `total_is_exact_sum` pins it.

## What the proofs caught that tests did not (showcase/transcript.txt)
- `by_category` that drops expenses over $1000: all 20 confirmed examples pass, 300/300 JS-style random states (amounts <= $100) pass; the proof of
  `by_category_sums_to_total` fails and the change is rejected. A $1500 rent shows `by_category = {}` vs `total = 1500`.
- `over_budget` with `>=`: examples pass; the random property test found it in only 1 of 300 states; the proof fails at `b ≤ ... vs b < ...`.
- A refactor of `total` (through `sum_cents`) keeps every example green but breaks turn 3's proof; the model must restate the law.
- False claims ("add_expense never fails", "top_category is never null") cannot be proved: rejected with the unsolved goal.
  A vacuous law, `sorry`, `native_decide` and `axiom` are rejected too.
- Static gate demos: `#eval`, `partial`, `unsafeBaseIO`, `IO`, `set_option`, `implemented_by`, instances, 2 commands, type errors,
  missing functions, non-terminating recursion (layer `termination`), and a terminating 3e9-iteration loop (1 s timeout -> ratchet/trace failures).

## Conformance probes and which gates caught them
side_effect (instance patch): static. breaks_ratchet: ratchet (+ proofs). breaks_invariant: ratchet, invariants, proofs. loops: termination.
calls_missing: static (unknown identifier). breaks_trace: ratchet, traces, proofs (the throwing `top_category` must be an `Except`, so its type changes).

## Limitations
No `Float`, no mutual recursion between forms, helper names must not collide with core names, strict arity, laws are only as good as
the statement (the kernel only insists it mentions an app function), runaway threads after a timeout are abandoned, a stack overflow in model code would abort the kernel.
The JSON-to-State boundary (cent rounding, codecs) and the kernel itself are trusted; only the app's functions are proved.
