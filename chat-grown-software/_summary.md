Geoffrey Huntley's idea of growing an application by chatting with a live image ([Jiti](https://github.com/ghuntley/jiti), in Common Lisp) is rebuilt in TypeScript on a `node:vm` realm, with a chat loop in which a model calls `develop`, `execute`, `preview` and `rollback` as tools, plus adapters for Claude (via the [Anthropic TypeScript SDK](https://github.com/anthropics/anthropic-sdk-typescript)) and DeepSeek. The headline numbers come from a scripted model. A first real run with DeepSeek exposed a kernel bug: a call written with semicolons became a syntax error that the user "confirmed" and no code could pass. The model proposes example calls but never expected answers: the kernel shows the user what each call returns and does to the state, adds its own questions (boundaries named in the user's words, repeated calls, calls for unobserved functions), and refuses "done" until every function in scope is covered. With contracts built only from those questions, answered by a simulated user who knows the intended program, seven verification layers caught 100% of 238 behaviour-changing slips in an expense tracker and 96% of 224 in a second shop scenario, against 90-97% with the examples as written. On 37 hand-written misunderstandings (coherent but wrong programs) they caught 30, against 26 with the written examples and 10 when the model graded itself. The simulated user never errs, so these are upper bounds.

- Machinery that needs nothing from the user (static checks, invariants, fuzzing, replay of real use) caught 67-75% of slips, but few misunderstandings.
- The question rules were designed on the first scenario. On the held-out shop scenario they only tied the user's own examples, because its boundaries live in the data ("fewer than 5"), not the arguments. Rules added afterwards closed part of the gap. Seven misreadings still pass every contract, each needing an input nobody mentioned.
- Code and data now roll back separately (rolling code back no longer deletes the expense recorded with a note), `execute` is exactly-once by request id (tested with a crash after commit), and each revision records the chat message that asked for it.
- The DeepSeek runs are judged by a simulated user who knows only the script's function names, so a model that names functions differently gets "corrected" toward throwing. That limits what a non-scripted run can show.
