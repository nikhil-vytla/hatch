# Chat-grown software in five languages: Clojure, Elixir, Smalltalk, Racket, Lean

The [parent folder](../README.md) rebuilt Geoffrey Huntley's
[Jiti](https://github.com/ghuntley/jiti) idea (grow an application by chatting with a live Lisp image) in
TypeScript, and worked out how to verify it: the model proposes code and example calls, the kernel shows the user
what the code actually does, and only the user's answers become the contract. This subfolder asks the follow-up: **is
TypeScript the right language for that kernel, and what does each language with a strong live-programming or
verification story give for free?**

Five kernels were built in parallel (Clojure, Elixir/BEAM, Pharo Smalltalk, Racket, Lean 4), plus the JavaScript
original as a baseline. All six speak one JSON-lines protocol, so one driver grows the same apps in each:
[DeepSeek](https://api-docs.deepseek.com/) (`deepseek-flash`) writes the code, a simulated user answers every
question, and hidden checks score the result. Each kernel also has a showcase of what its language does that the
others can't, applied to a modern problem (an LLM API gateway), recorded as video.

## The short answer

- **For getting the code right, the language barely matters; for verifying it, it matters a lot.** DeepSeek grew
  both apps correctly in JS, Clojure, Elixir and Smalltalk (100% or 98% of hidden checks over 3 runs each), Racket
  95-100%. Lean scored 83-91% and cost 3-12x the output tokens and 3-10x the time, because it also has to prove things.
- **What the languages change is what the kernel can know before running anything**, and how much it can do to a
  live system safely:
  - *Code as data* (Clojure, Racket, Smalltalk's AST, Elixir's quoted forms, Lean's type checker): a call to a
    function that doesn't exist, a top-level side effect, or a redefined builtin is refused **statically**. JavaScript only notices when a
    test happens to run it.
  - *A real sandbox* (Racket): file, network, process access and memory bombs are contained; the same attacks in
    `node:vm` read `/etc/passwd`, ran `id`, and crashed the host with a heap bomb.
  - *Hot code loading with state migration* (Elixir): the TypeScript project's biggest gap ("a verified migration
    path") closes: the stored data is reshaped while 5 clients keep calling: 564 requests, 0 unexpected failures.
  - *The live image* (Smalltalk): fastest kernel (25 ms per change), method-level hot fixes and rollback, the change
    log as the audit trail, and save-and-restart of code + data + history together.
  - *Proofs* (Lean): laws like "no key ever exceeds its quota" are proved for all inputs and re-proved on every
    change. Three plausible bugs passed 19/19 examples and 300/300 random tests and were refused by the proof.
- **Strict languages refuse things JavaScript silently allows.** Rolling `add_expense` back to its 2-argument
  version while a recorded 3-argument call exists: every other kernel refuses; JavaScript "succeeds" because it
  ignores extra arguments.
- **Why Lisp, then?** Probably for all of the above at once (code is data, the image is live, conditions and
  restarts, CLOS migrates instances on redefinition), at the cost of models writing less Lisp. In this benchmark
  that cost did not show: DeepSeek's Clojure and Racket were as correct as its JavaScript, at 1.3-1.8x the output
  tokens.

## Benchmark: DeepSeek grows the same apps in six kernels

Two scenarios, 3 repetitions each, same driver, same simulated user, same questions
(`results/benchmark.md`, regenerated by `bench/aggregate.ts`):

**Expense tracker (8 turns, 20 hidden checks per run)**

| kernel | hidden goal checks | final regression | develops / run | user corrections / run | output tokens / run | minutes / run |
|---|---|---|---|---|---|---|
| JavaScript | 60/60 (100%) | 60/60 | 11.3 | 10.7 | 22k | 1.9 |
| Clojure | 59/60 (98%) | 59/60 | 11.3 | 7.0 | 35k | 3.0 |
| Elixir | 60/60 (100%) | 60/60 | 13.0 | 11.3 | 39k | 3.3 |
| Smalltalk | 60/60 (100%) | 60/60 | 11.3 | 6.7 | 28k | 2.5 |
| Racket | 57/60 (95%) | 57/60 | 13.3 | 9.7 | 41k | 3.6 |
| Lean 4 | 50/60 (83%) | 50/60 | 11.3 | 4.3 | 132k | 9.9 |

**LLM API gateway (5 turns, 19 hidden checks per run)**

| kernel | hidden goal checks | final regression | develops / run | user corrections / run | output tokens / run | minutes / run |
|---|---|---|---|---|---|---|
| JavaScript | 57/57 (100%) | 57/57 | 7.3 | 10.3 | 15k | 1.2 |
| Clojure | 57/57 (100%) | 57/57 | 7.7 | 8.7 | 20k | 1.7 |
| Elixir | 57/57 (100%) | 57/57 | 7.0 | 6.0 | 13k | 1.1 |
| Smalltalk | 57/57 (100%) | 57/57 | 7.7 | 6.0 | 18k | 1.5 |
| Racket | 57/57 (100%) | 57/57 | 6.7 | 3.7 | 25k | 2.1 |
| Lean 4 | 48/57 (84%) | 52/57 | 8.0 | 4.0 | 163k | 11.2 |

*Hidden goal checks*: after each turn, the scenario's own examples run on the live code and are compared with the
intended program; the model never sees them. *Final regression*: all turns' examples on the final code.
*Corrections*: answers the simulated user changed after seeing what the candidate code did.

Where points were lost:
- **Lean**: 6 turns (of 39) ended at the 10-step limit with no accepted change. The proof gate refuses drafts and
  DeepSeek spends its steps re-proving. It also needed far fewer user corrections: proofs force it to pin down
  behaviour before the user sees it.
- **Racket** (one run): DeepSeek called `try` (preview) 10 times at the budgets turn, 54 forms, and never
  submitted; the user was never asked. A dithering failure, not a language one; a driver nudge would fix it.
- **Clojure** (one run): `over_budget` wrong on one example of one turn.

## The kernels

All pass the same 51-check conformance suite on the expense tracker and 28 checks on the gateway
(`results/conformance-*.txt`): the scenario turns with their own reference code, six probes (top-level side effect,
ratchet break, invariant break, infinite loop, call to a missing function, trace break), stale generation,
exactly-once execution (also across a restart), throw atomicity, `why`, code-only rollback and restart.

| | start | develop | missing function caught by | infinite loop | the language layer |
|---|---|---|---|---|---|
| [JavaScript](js/) (baseline) | 0.1 s | ~100 ms | tests (ratchet) | 2 s, timeout | none: `node:vm` with frozen intrinsics |
| [Clojure](clojure/) | 0.4-0.6 s | ~80 ms | **static** (code as data) | 1 s, injected deadline checks | forms read as data and walked against an allowlist; persistent state history (20,001 states in 7.7 MB) |
| [Elixir](elixir/) | 0.3-0.5 s | ~55 ms | **static** (AST walk) | 1 s, process killed | hot code loading, two versions live; `migrate` reshapes running state; every eval in a killable process |
| [Smalltalk](smalltalk/) | 0.15-0.7 s | **~25 ms** | **static** (unknown `self` send) | 1 s, process terminated | methods compiled into a live class; Epicea change log; image save/restart; per-method rollback |
| [Racket](racket/) | 0.3-0.4 s | ~110 ms | **static** (free identifiers after expansion) | 1 s, custodian kill | `racket/sandbox`: security guard, memory and time limits |
| [Lean 4](lean/) | 0.3-0.7 s | ~350 ms | **static** (type checker) | **refused**: termination checker | live `Environment` in-process; laws are theorems re-proved on every change; money as exact `Int` cents |

The Lean kernel elaborates each change into an in-process `Lean.Environment` and runs it with `evalConst`: a true
live image, not a compile-per-request loop. Its trade-offs: no `Float` (money is integer cents; sub-cent inputs are
quantised), laws must be restated when a function they mention changes, and a runaway call is abandoned, not killed.

## Findings beyond the numbers

- **A simulated user is only as good as its reference program.** In the first runs DeepSeek proposed
  `add_expense(-5, "food")` at turn 1. The turn-1 reference program stores it, so the user "confirmed" a state that
  breaks the user's own invariant, and no code could satisfy both. Fixed: the user's invariants hold from the first
  turn. All runs before the fix were discarded.
- **Read the model's output cap before reading its scores.** Lean's first run lost two whole turns to an 8000-token
  cap (DeepSeek reasons at length before writing Lean). The cap was raised to 32000 and every run repeated; one
  Lean run still hit it.
- **Reads that write.** DeepSeek's `usage("nobody")` on an empty gateway left `{calls: []}` behind. No question
  covered an empty state, so the user never saw it; the hidden checks did. The question rules should add the empty
  fixture for every function in scope.
- **Behaviour the examples don't exercise is unguarded in every language but Lean.** The Racket injection showcase
  and the Lean showcase are two views of the same fact: gates built from examples and traces catch what was asked
  about; proofs catch what holds for all inputs; nothing here compares error *text*, so a leak through an error
  message passes everything.
- **Fixed arity is a safety feature.** Clojure, Elixir, Racket, Smalltalk and Lean all refuse the code-only rollback
  that JavaScript performs, for a good reason (a recorded call would no longer run).
- **Traces grow.** Every trace stores its before-state, so the Elixir kernel's data file grew quadratically under
  load; it now keeps the most recent 1000. Clojure's structural sharing is the better answer (history costs about
  1.6x one copy of the state).
- **Safety boundaries held for the subagents too.** The Smalltalk agent's first operator console had an `eval`
  op; the auto-mode classifier denied it as a code-execution surface and the agent built read-only `inspect`
  queries instead. Left that way.

```
scenario/            expenses.json, gateway.json (+ gateway.reference.js, the intended program and invariants)
bench/               kernel-client.ts, reference.ts (the simulated user), conformance.ts, grow.ts (DeepSeek
                     driver), reps.sh, aggregate.ts
js/ clojure/ elixir/ smalltalk/ racket/ lean/
                     one kernel each: run.sh, setup.sh, reference.json (+ reference-gateway.json), prompt.md,
                     showcase/ (script + transcript), NOTES.md, README.md
results/             <scenario>-<lang>-r<n>/ (events.jsonl, summary.json, final-code.json), benchmark.md/.json,
                     conformance-*.txt
video/               player.html, build.ts, record.ts (Playwright + ffmpeg), showcases.sh
videos/              the seven recordings (mp4, each under 2 MB)
```

Run a kernel's conformance check from `chat-grown-software/languages/` (after the kernel's `setup.sh`):

```
node --experimental-strip-types --no-warnings bench/conformance.ts clojure
SCENARIO=gateway node --experimental-strip-types --no-warnings bench/conformance.ts clojure
```

Grow an app with DeepSeek (needs `DEEPSEEK_API_KEY`, or a proxy that injects it plus `NODE_USE_ENV_PROXY=1`):

```
SCENARIO=gateway node --experimental-strip-types --no-warnings bench/grow.ts lean
```

Toolchains used: Elixir 1.14 (OTP 24/25), Racket 8.10 CS, Clojure CLI 1.12 on Java 21, Lean 4.34.1, Pharo 12, Node 22.

## Limits

- One model (`deepseek-flash`), 3 repetitions, two small scenarios. Differences of one or two checks are noise.
  Token counts include DeepSeek's reasoning and depend on how verbose each language's prompt makes it.
- The user is simulated and never wrong; real users are slower and sometimes are. Results are upper bounds.
- The JS baseline kernel and the simulated user reuse `../prototype/src/` (`world.ts`, `scenario.ts`, `sim-user.ts`),
  and the driver uses the prototype's chat-loop types and DeepSeek adapter: changing those changes these results.
- Each kernel was written by a Sonnet subagent in about 10-25 minutes and verified by re-running its conformance;
  their code is reviewed through those checks and the showcases, not line by line.
- The sandboxes are in-process (Racket's sandbox, Elixir processes, Pharo processes): containment, not an OS
  boundary. Lean and Clojure abandon, rather than kill, a runaway thread.
- Lean's kernel uses integer cents, so its money semantics differ from the others at sub-cent inputs; the
  scenarios' values are all whole cents.
- The showcases were designed to demonstrate each language's feature; they are demonstrations, not benchmarks.
