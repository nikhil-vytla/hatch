Shareware Doom now runs inside the browser DevTools console as a [Text.js](https://textjs.org) App Router page. The stock [doomgeneric](https://github.com/ozkl/doomgeneric) sources compile unmodified to a 402 KB wasm32-wasi module with `zig cc`, and a ~150-line in-memory WASI shim runs that module. The page draws Doom's framebuffer through Text.js's `<Image>` as half-block cells and reads raw keydown/keyup for held keys. The same page also plays in a terminal via `text run` and passes Text.js's offscreen tests. Screenshots of a headed Chromium under Xvfb show real gameplay in the Console panel. The interesting result is about performance: the DevTools Console panel, not Doom or Text.js, limits the frame rate.

- A Doom frame is about one `%c` span per cell (~7.5k spans, ~1.2 MB at 160×61). RLE barely helps, and ~110 bytes of repeated font CSS per span dominates the payload.
- The Console panel renders only ~17–22k spans/s and queues everything else. At Text.js's normal ~15 fps it fell 80–120 frames (10–15 s) behind. Pacing frames to a span budget keeps the lag at a few frames.
- The best playable setting measured is 80×31 cells at ~6–9 fps in DevTools. The same page reaches ~20 fps in a terminal at 120×46 cells, with ~27 KB of row-diffed ANSI per frame.
