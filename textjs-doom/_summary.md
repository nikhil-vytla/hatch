Shareware Doom runs inside the browser DevTools console as a [Text.js](https://textjs.org) App Router page. The stock [doomgeneric](https://github.com/ozkl/doomgeneric) sources compile to a ~400 KB wasm32-wasi module with `zig cc`, and a small in-memory WASI shim runs it. The page draws frames as half-block cells through Text.js's `<Image>`, plays sound effects and synthesized music with Web Audio, and the same page also runs in a terminal via `text run`. The main result is that the DevTools Console panel, not Doom or Text.js, limits the frame rate. A second round, with code drafted by deepseek-flash and reviewed and measured by hand, raised the rate DevTools can actually display by 2.4–4x.

- A full-colour frame is about one `%c` span per cell (~7.5k spans, ~1.2 MB at 160×61), and DevTools draws only ~17–22k spans/s. At Text.js's normal ~15 fps it fell 10–15 s behind; pacing by span budget bounds the lag.
- The page cannot observe DevTools: remote `background-image` URLs in `%c` styles are never fetched, and custom formatters are off by default.
- Bytes per span matter. Stripping Text.js's repeated font CSS (`css=min`) raised DevTools fps from 4.9 to 8.1 at the same span count.
- Adaptive span shaping merges near-identical neighbouring cells to hit a span target. With default settings DevTools shows 7.1 / 7.1 / 5.4 fps at 100×38 / 120×46 / 160×61 cells, up from 3.0 / 2.1 / 1.3, with mean pixel error of 2.5–5.3 out of 255 and about 1 s of lag.
