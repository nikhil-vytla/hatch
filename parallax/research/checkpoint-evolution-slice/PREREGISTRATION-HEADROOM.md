# Preregistration: budget-headroom disambiguation run

Status: **preregistered before spend; committed before the first paid
call.** Follow-up to the executed screening in
[PREREGISTRATION-DRAFT.md](PREREGISTRATION-DRAFT.md) /

## Question

The first screening separated the arms completely at stage 3: evolved
0/10 verifiable (all budget RunFailures at 4802–4864 bytes against the
4096-byte cap), carry-reference 10/10 strict. That result is
confounded: the evolved arm is the only arm that must re-serialize its
own accumulated workspace in every full-file-map reply, so the flat
per-stage cap gives the two arms *nominally* matched budgets but
*effectively* unmatched ones — the budget guaranteed to remain for new
stage content in the evolved arm is the cap increment, which is zero
for flat caps. The two live explanations:

- **H-accumulation**: extending its own prior workspace degrades the
  agent's ability to satisfy accumulated obligations (a real
  checkpoint-evolution finding).
- **H-instrument**: full-file-map replies plus the flat 4096-byte cap
  mechanically guarantee the stage-3 failure, and the separation is an
  artifact of the design.

RQ: with byte pressure removed and everything else identical, does the
evolved arm still verify differently from carry-reference?

## Design (one lever: the mechanical output ceiling)

Identical to the executed screening — same `ce-tally-1` specs, sealed
cases, contract, references, same 10 trial seeds (101–110), same two
arms, same model (`claude-haiku-4-5`), same sandbox, same evidence
pipeline — except the output ceilings:

| Field | Original | Variant (`ce-tally-1-headroom`, digest `f369…5812`) |
|---|---|---|
| Workspace byte caps | 4096 / 4096 / 4096 | 4096 / 8192 / 12288 |
| Max output tokens per call | 2048 | 4096 |

The cap schedule satisfies the new structural rule
(`budget_headroom_violations` empty at factor 2): every cap increment
covers at least twice the reference increment, so any *legal* carried
workspace leaves at least twice the reference-sized budget for new
content. Stage-3 room is comfortable in both arms: the observed evolved
attempts (≤ 4864 bytes) fit in 12288 with 2.5× slack. The token ceiling
rises with the byte cap because a maximal legal 12288-byte reply does
not fit in 2048 tokens — leaving it would move the same mechanical
ceiling from bytes to tokens, not remove it. Reply format is unchanged
(full file map): the reply-format lever is deliberately *not* pulled,
so this run changes exactly one thing — the mechanical output ceiling.

## Outcome mapping (declared before the run)

- Evolved stage-3 budget RunFailures drop to ~0 **and** evolved
  verdicts are comparable to carry (paired strict differences whose
  bounds include 0 at stages 2 and 3) → **H-instrument**: the original
  separation was manufactured by the instrument. Say so bluntly; the
  headroom rule (already enforced on the live path) is the fix.
- Evolved stage-3 failures persist as *case-level* regressions or
  verdict deficits (strict fails while carry passes, decisively over
  the 10 pairs) → **H-accumulation** is supported at screening grade.
- Mixed or partial (e.g. failures move from budget to token
  truncation, or verdicts split) → report the split verbatim;
  no headline claim.

Bounds-only language; one family is one cluster; no clustered interval.

## Cost estimate and stop rules

Same 60-call design. Upper bound via `ce_cost_upper_usd` with the
larger caps and 4096-token ceiling: ≈ $1.5 (larger prompt-size proxy
and doubled output allowance), against the unchanged **$5 hard cap**.
Expected actual, extrapolating from the first run: $0.30–$0.60. Stop
rules unchanged: hard-stop at the cap; stop and diagnose if
RunFailures exceed 30% of stage calls or on any evidence-validation
error; abort after > 3 consecutive gateway connection failures.
