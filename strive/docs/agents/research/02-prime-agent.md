## Source-supported facts

**What it is.** A TypeScript monorepo implementing an interactive/headless coding and research agent ("Prime Agent: A Self-Improving RLM Agent", `README.md`). Packages: `packages/coding-agent` (the product), `packages/agent`, `packages/ai` (provider layer), `packages/tui`, plus `prime-agent-runtime/` — a Python package loaded into an IPython kernel. 237 test files under `packages/coding-agent/test/`.

**Two core abstractions** (`README.md`, `packages/coding-agent/docs/rlm.md`):

1. **RLM (Recursive Language Model) runtime** — the model's single built-in tool is a persistent IPython kernel; file ops, shell, skills, and subagent spawning all happen as Python code. Kernel state (variables, imports, handles) survives across tool calls and compaction. A preloaded callable `rlm("task")` spawns a real child `AgentSession`; the call returns an admission handle immediately (`rlm_child_id`, `name`, `session_dir`, `model`) and never the child's answer — results arrive only via explicit `agent_message` replies or files (`docs/rlm.md`, `docs/rlm-runtime.md`).
2. **Continual Harness** — durable, editable supplemental state in four kinds: `prompt` notes, `memory`, `skill` descriptions, `subagent` specs. Refined by an LLM pass (`/refine`) that emits small create/update/delete edits, with recorded history and rollback (`packages/coding-agent/src/core/refinement/refinement.ts`, 1017 lines; tests in `test/refinement.test.ts`, 1519 lines).

**Process architecture** (`docs/architecture.md`): TUI/headless clients → daemon supervisor (routing, attachments, recovery) → one session worker per root session tree (holds `AgentSessionRuntime`, root `AgentSession`, scheduler, root IPython kernel, RLM child runtimes) → model providers and session storage. Workers and kernels are separate OS processes explicitly "for lifecycle and failure containment, not security sandboxes." The TS↔Python boundary is the Jupyter protocol over ZeroMQ; Python calls back into the host via a comm target `host.request` with typed requests (`docs/rlm-runtime.md`); "The Python side does not call providers or implement an agent loop."

**Persistence** (`docs/session-format.md`, `src/core/session-manager.ts`): sessions are append-only JSONL files at `~/.prime/agent/sessions/<id>.jsonl`. Entries form a **tree** via `id`/`parentId`, enabling in-place branching; the "leaf" is the current position. Entry types include `message`, `compaction` (summary + `firstKeptEntryId` + `tokensBefore`), `branch_summary` (LLM summary of an abandoned branch), `custom` (extension state, excluded from LLM context), `custom_message` (injected into context), `label`, `child_usage_attributed`, `session_state`, `git_state` (append-only repo snapshot for recovery views). Versioned header with automatic migration (v1 linear → v2 tree → v3).

**Continual-harness data model** (`refinement.ts` lines 34–63): `HarnessEntry {id, kind, title, content, path, scope: "local"|"global", reference, arguments, metadata, source, created_at, updated_at, version}`; `HarnessState {schema, entries per kind, refinements: HarnessRefinementEvent[]}` where each refinement event records `{id, trigger, changes, evidence, outcome, created_at}`. State lives in `harness_state.json` — global under `~/.prime/agent/harness/`, local under the session artifact dir (`getGlobalHarnessStateDir`/`getLocalHarnessStateDir`). Saves are atomic (temp file + `renameSync`, mode preserved, default `0o600`; `saveHarnessState`). A corrupt state file degrades to empty rather than crashing the session (`loadHarnessState` comment, lines 292–299). Local and global stores are merged for prompting with collision-safe scope-prefixed ids (`mergeHarnessStates`).

**The refinement loop** (`refinement.ts`, `src/core/agent-session.ts`):

- `planRefinement` sends the serialized conversation (last 80k chars), a compact harness overview, and the last 20 refinement results to a model with a fixed system prompt; the model returns JSON `{summary, rationale, expectedOutcome, edits[]}` only. Plan and apply are deliberately split so the harness file can be re-read just before applying — "the LLM call here can take many seconds, during which the kernel or another session may write the shared harness_state.json" (doc comment, lines 856–862).
- `applyRefinementProposal` validates each edit (`validateEdit`): the **base system prompt is not editable** (id `base_system_prompt` rejected, including when derived from a title — tests at `refinement.test.ts:931,957`); skill entries must carry a `reference` of `{"type":"python"}` with import + callable and an `arguments` contract. Edits against entries that changed since planning are rejected with "entry changed during refinement planning" (optimistic concurrency via `baselineState`, lines 727–740).
- Every applied edit records **before/after entry snapshots** (`AppliedRefinementEdit`), and entry `version` increments on update.
- Results are journaled twice: as a `CustomEntry` with `customType: "prime-agent.refinement"` in the session JSONL, and — for global scope — appended to an append-only `refinements.jsonl` in the global harness dir so they "can be rolled back from any session" (`appendGlobalRefinement`, lines 369–379). Malformed history lines are skipped, "so a single bad append cannot break rollback."
- **Rollback** (`rollbackProposal`, lines 804–836): a rollback is itself a refinement whose edits invert the target's applied edits in reverse order from the recorded before/after snapshots (recreate deleted, delete created, restore updated). Invoked via `/refine rollback <id>` (`src/core/slash-commands.ts:42–53`), works cross-session for global refinements via the history file (test at `refinement.test.ts:1419`).
- **Auto-refine** (`reviewAutoRefine`; `agent-session.ts` ~2180–2570): a cheaper LLM "review gate" runs on triggers `turn_interval` (default every 25 assistant turns, `settings-manager.ts:25`) or `compact`, and decides `{shouldRefine, rationale, instructions}`. Enabled by default (`settings-manager.ts:839`). Auto-refines default to **local** scope; the gate prompt explicitly rejects "one-off noise, unsupported hypotheses, and transient tool outputs."
- **Scope policy** (system prompt in `refinement.ts:140–148`): local = session-scoped progress/blockers; global = "stable cross-session lessons, durable user preferences, reusable skills/subagents." During a local refinement, global entries are read-only; the model must shadow with a local entry instead of editing them.
- The kernel-side `refine` skill (`packages/coding-agent/skills/refine/SKILL.md`) lets the model itself schedule refinement (`await refine.run(...)`); "Refinement never runs mid-cell. A scheduled refinement runs when the current turn ends; the harness applies changes and rebuilds the system prompt, then resumes you automatically."

**Prompt injection of harness state** (`src/core/system-prompt.ts:105–141`, `formatHarnessStateForPrompt`): the merged harness is rendered into the system prompt as a truncated overview (defaults: 6 entries/kind, 5 recent refinements, 180 chars/entry) with an explicit statement: "The base system prompt is immutable; prompt entries below are supplemental notes only," plus instructions on when to call `refine.run()`.

**LLM-output failure handling** (`refinement.ts:564–631`): output budget is derived from the model (`Math.min(model.maxTokens, 32_000)`); truncated JSON is distinguished from malformed JSON by a brace/string-balance scan (`isIncompleteJson`) so exhausted budgets get a named error instead of a confusing parse error; `stopReason === "length"` and `"error"` are handled explicitly; refinement requests are forced non-reasoning so the output budget goes to the JSON object (comment at lines 907–912).

**Autonomous mode** (`src/core/autonomous.ts`): bounded continuation with default budgets `maxContinuations: 3`, `maxTurns: 12`, `maxTokens: 80_000`, `timeoutMs: 30 min`, plus **quality gates** — user-configured shell commands with `maxRetries: 3` and a 5-minute timeout each; a git-worktree snapshot (`status` + `diff` + hash of untracked files) is captured on gate failure. The continuation prompt tells the model "the verifier/evaluator decides completion when configured gates pass," and the README warns "A passed gate checks only what that gate verifies; reaching a limit does not imply task success."

**Observation:** the `agent-observe` Python skill (`skills/agent-observe/SKILL.md`) provides strictly read-only inspection of parent/siblings/children sessions with bounded message previews; `git_state` entries and `src/core/agent-traces.ts` record repository state and traces. Long-running features: goals (`skills/goal`), heartbeats, cron schedules, daemon-backed detach/reattach (`docs/long-running-agents.md`, README).

**Trust/safety statements:** README warning — "Prime Agent executes model-generated Python and project commands with your user permissions. Its worker and kernel processes improve lifecycle isolation and recovery; they are **not** a security sandbox." `docs/rlm.md` "Trust Model" and "Host Bridge" — credentials, provider execution, transcript writes, worker routing, and scheduling stay in the TypeScript host; Python skills reach host state only via typed `rlm.host_request(...)`.

**Python mirror of the harness:** `prime-agent-runtime/src/rlm/harness.py` re-implements the same `HarnessEntry`/state model as dataclasses with env-var-based store routing (`RLM_HARNESS_STATE_DIR`, `RLM_SESSION_DIR`, global fallback) so kernel-side code can read/write harness state; docstring: "Execution still belongs to Prime Agent's TypeScript host."

**Relation to RL training:** the README links Verifiers and PRIME-RL as sibling Prime Intellect projects; nothing in this repo trains weights.

## Analysis dimensions

**Runtime, task, environment, and state models.** Runtime: client → daemon supervisor → per-root-session worker process → `AgentSession` → IPython kernel process(es) (`docs/architecture.md`). "Task" is conversational (a prompt/goal), not a typed task object with expected outputs; the closest formalizations are persistent goals (`skills/goal`) and autonomous-mode gates (`autonomous.ts`). Environment = the user's real cwd with user permissions. State: session JSONL tree + kernel state (snapshot/restore machinery in `src/core/kernel/state-snapshot.ts`, tests `kernel-state-roundtrip.test.ts`) + harness JSON stores.

**Observation, trajectories, traces, memory, persistence.** The session JSONL is the trajectory: every message, tool result, compaction, branch, model change, and refinement result is an append-only entry with parent links (`docs/session-format.md`). Refinement consumes the serialized trajectory directly as evidence. Memory is explicit and typed (the four harness kinds) and versioned per entry. `agent-observe` gives read-only cross-agent observation. Kernel variables are a second, non-journaled state layer (snapshot-restorable but not an audit record).

**Trusted/immutable vs evolvable surfaces.** Clearly drawn and mechanically enforced: the base system prompt is immutable (validator rejects `base_system_prompt` edits in trusted TS code, not just in prompt text); provider calls, credentials, scheduling, child lifecycle, transcript writes, and the refinement apply/validate logic live in the trusted TypeScript host. Evolvable: the four harness-entry kinds, plus installed skills as code (via the separate `skill-creator` packaging workflow — README distinguishes `/refine` from "packaging and reviewing new executable skills"). The refinement pipeline itself (system prompts, validators, apply logic) is not evolvable.

**Recursive decomposition, subagents, context management.** First-class: `rlm(...)` spawns real child sessions with independent context and session dirs, inheriting model/skills/tools unless overridden; recursion depth is configurable (`src/core/rlm-max-depth.ts`, default allows root→children). Fire-and-forget admission with results via messages/files decouples parent context from child transcripts; child usage is attributed to the parent (`child_usage_attributed` entries). Context management: automatic compaction with summaries preserving recent messages and kernel state, branch summaries on tree switches, and the "prompt-as-a-variable" pattern of keeping working state in Python rather than in tokens.

**Candidate generation and self-modification.** Generation is a single LLM pass (`planRefinement`) constrained to a JSON edit schema over an allowlisted surface; edits are "small, evidence-backed updates," with the prompt instructing the smallest relevant component (memory vs skill vs prompt note vs subagent spec). Self-modification is real (the agent can call `refine.run()` on itself) but structurally bounded: schema validation, immutability rules, scope policy, concurrency baseline check, and turn-boundary application.

**Evaluation, selection, promotion, rollback, lineage.** The weakest dimension by strive's standards. There is **no empirical validation of a refinement**: `expectedOutcome` is a free-text field ("what should improve and how to validate it") that nothing executes. Selection is LLM judgment before the fact (the auto-refine review gate) plus human/model judgment after the fact (the refinement prompt says "If prior refinements caused issues, rollback or replace the faulty editable entries"). Promotion exists as the local→global scope distinction, gated by policy text, not by measurement. Rollback and lineage are strong: per-edit before/after snapshots, entry version counters, append-only refinement history, cross-session rollback, rollbacks that are themselves journaled refinements. Autonomous-mode quality gates are the only executable acceptance checks, and they gate task continuation, not harness changes.

**Sandboxing, secrets, permissions, budgets, recovery.** No sandbox by design and documented as such; process separation is for fault containment. Secrets stay host-side (auth storage, host bridge). Budgets exist for autonomous mode (turns/tokens/time/continuations) and for refinement output tokens, not for evaluation cost (there is no evaluation). Recovery is substantial: daemon crash-recovery snapshots (`docs/agent-connection.md` referenced from architecture doc), orphan-process journal (`src/core/orphan-process-journal.ts`), worker/command recovery journals (tests `worker-recovery-journal.test.ts`, `command-recovery-journal.test.ts`), corrupt-state degradation to empty, malformed-history-line tolerance.

**Online adaptation vs offline optimization.** Purely online: refinement runs inside live sessions at turn boundaries, triggered by turn count, compaction, user command, or the model itself. There is no offline benchmark/optimization loop in this repo (that role belongs to the linked Verifiers/PRIME-RL projects).

**Harness adaptation vs model-weight learning.** Entirely harness adaptation — prompts-around-the-model, memories, skill/subagent specs. No fine-tuning, no gradients. The "RLM" name refers to the recursive runtime, not to RL on weights.

**Genuinely self-improving vs merely persistent/configurable.** Between the two. Against strive's four-part definition of "learning from itself" (charter): refinements are (1) motivated by the system's own trajectory evidence, (2) produced by the system's own proposal mechanism on a declared evolvable surface, and (4) retained durably with lineage and reversibility — but (3) **empirical validation is absent**. By strive's charter, an unvalidated model rewrite "is not learning"; prime-agent is a highly engineered persistence-and-self-modification layer whose acceptance rule is LLM/human judgment rather than measurement.

**Mechanisms suitable for a robust, long-lived harness.** The strongest exports: append-only JSONL trajectory with tree structure and derived context; atomic temp-file+rename state writes with graceful corrupt-state degradation; per-edit before/after snapshots enabling inverse-edit rollback; rollbacks journaled as first-class operations; immutability enforced in trusted code; plan/apply split with optimistic-concurrency baseline; scope tiers (local vs global) controlling blast radius; cheap review gate before expensive refinement; typed host bridge keeping secrets/state out of the evolvable runtime; explicit truncation-vs-malformed diagnosis of LLM JSON output; turn-boundary-only application of self-modifications.

## Interpretations

(Inferences, not source claims.)

- **The missing evaluator is a deliberate product tradeoff, not an oversight.** Prime-agent optimizes for interactive usefulness across long sessions, where "did this memory help?" has no cheap ground truth. Its compensations — small edits, review gate, easy rollback, local-by-default scope — are all ways of keeping the cost of a *wrong* self-modification low instead of proving a modification *right*. That is the inverse of strive's bet (prove it right before accepting).
- **The `expectedOutcome` field looks like a validation hook that was never wired to an executor.** Its prompt text ("how to validate it") reads as an intended future gate. It currently functions only as documentation for later refinement passes reading the history.
- **Inverse-edit rollback vs strive's activation-pointer rollback**: prime-agent must invert edits because its evolvable state is a mutable keyed store edited in place; strive's generations are immutable artifacts, so rollback is just re-activation. The prime-agent approach buys fine-grained multi-entry state at the cost of rollback complexity (their `rollbackProposal` must reverse-order edits and handle create/update/delete asymmetries; strive's rollback is one journal line).
- **The four-kind taxonomy (prompt/memory/skill/subagent) is a practical answer to strive's research question 4** (minimal set of evolvable surfaces). Notably, "policy parameters" and "code" are absent from the refinable set — executable skill *code* goes through a separate, human-reviewable packaging path (`skill-creator`), while `/refine` only edits skill *descriptions/contracts*. That's a two-tier trust model for evolvable surfaces: metadata evolves cheaply; code evolves through a heavier gate.
- **The auto-refine review gate is a cost-control pattern**: a small-budget LLM call (4k tokens) decides whether the large-budget refinement call (32k tokens) is worth running. Validation effort scaled to expected value, which strive's charter lists under Efficiency.
- **Self-modification only at turn boundaries** ("never runs mid-cell", system prompt rebuilt afterwards) is a concurrency discipline: the evolving surface never changes underneath an in-flight reasoning step.

## Hypotheses to test in strive

1. **Judgment-gated vs empirically-gated acceptance.** Implement a prime-agent-style LLM review gate as a *pre-filter* before strive's empirical validation. Hypothesis: it cuts wasted candidate evaluations substantially at negligible quality cost; measure rejected-candidate eval spend with/without the gate.
2. **Unvalidated memory-style surfaces drift.** Add a "memory" evolvable surface accepted prime-agent-style (no empirical gate, snapshot + rollback only) alongside empirically validated strategy code. Hypothesis: over many cycles, unvalidated entries accumulate stale/wrong content (measurable as score regression when the memory is injected vs ablated) — quantifying exactly why strive's charter demands validation.
3. **Scope tiers as a promotion ladder.** Test local(per-task)→global(cross-task) promotion where global promotion requires validation on a *second* task suite. Hypothesis: this contains overfitting-to-one-task better than a single shared surface (charter research question 5, credit assignment across tasks).
4. **Inverse-edit vs re-activation rollback under multi-surface evolution.** When strive reaches composite generations (prompt + code + policy in one cycle, HANDOFF "lineage under multiple surfaces" risk), compare prime-agent-style per-edit before/after snapshots against whole-artifact re-activation for rollback correctness under partial failures.
5. **Optimistic-concurrency baseline for slow proposers.** Once `ModelProposer` lands (slow calls), test the plan/apply split with a baseline check: reject acceptance if the incumbent changed during proposal. Hypothesis: prevents lost-update races when cycles overlap or a human edits mid-cycle.
6. **Structured proposal schema + truncation diagnosis.** Adopt JSON-schema-constrained proposals with prime-agent's balanced-brace truncation detection. Hypothesis: named failure modes (truncated vs malformed vs invalid-edit) make model-proposer failures diagnosable from the ledger alone (charter: observability).

## Mechanisms: early prototype vs mature harness

**Adopt now (cheap, matches strive v0's shape):**

- **Atomic state writes** (temp file + rename) for the ledger and generation files — `saveHarnessState` pattern; strive's JSONL appends are already safe, but any derived snapshot/index (HANDOFF tech debt) should be written this way.
- **Corrupt-artifact degradation as recorded outcome**: `loadHarnessState` returns empty instead of throwing; strive's equivalent is treating an unreadable generation file as a recorded failure, never a loop crash (charter: Reliability).
- **Rollback as a first-class journaled operation carrying `rollbackOf`** — strive already journals activations; add an explicit reason/`rollbackOf` field so lineage queries can distinguish rollback from ordinary promotion.
- **Named LLM-output failure taxonomy** (truncated/malformed/invalid) in the proposer interface *before* the model proposer exists, so the registry proposer and fake-model tests pin the contract.
- **Immutability enforcement in trusted code** — strive already does this structurally (evolvable surface = strategy file only); keep the prime-agent lesson that the rule must live in the validator (`validateEdit`), not in prompt text, when the proposer becomes a model.

**Adopt at stage 2–3 (model-in-the-loop, multiple surfaces):**

- **Plan/apply split with baseline re-read** for slow model proposals.
- **Review gate** (cheap model call) ahead of full propose+validate, with the gate's verdict journaled.
- **Local/global scope tiers** when strive grows a second task: per-task evolvable state vs promoted cross-task state, promotion requiring held-out validation.
- **Per-edit before/after snapshots** once generations become composite (multiple surfaces per cycle).
- **Two-tier evolvable surfaces**: metadata/config evolves under lightweight gates; executable code only under the full empirical gate — prime-agent's refine-vs-skill-creator split, but with strive's validation replacing human review for the code tier.

**Defer / treat as cautionary:**

- The full daemon/worker/kernel process architecture — solves interactive long-running-session problems strive doesn't have (charter non-goal: distributed orchestration).
- Turn-interval auto-refine into an unvalidated store — this is the pattern strive exists to improve on; only import it *with* an empirical gate attached.
- Tree-structured session branching — powerful for interactive exploration; strive's linear cycles + lineage parents already cover the evolution use case.

## Implications for strive

1. **The proposer interface should emit structured edit lists, not opaque patches.** Prime-agent's `RefinementProposal {summary, rationale, expectedOutcome, edits[]}` with per-edit `reason` is a good shape for strive's stage-2 `Proposer` protocol: it gives the ledger a machine-checkable record of *what* changed and *why*, per surface, and gives `decide` something to validate edit-by-edit. Strive should add one field prime-agent lacks teeth for: `expectedOutcome` as an *executable claim* (e.g., "case 7 now passes") that validation checks, closing the loop prime-agent leaves open.
2. **Validation stays mandatory; add the cheap gate in front, not instead.** Prime-agent demonstrates the full spectrum of compensations you need when you drop empirical validation (small edits, review gates, snapshots, easy rollback, scope containment). Strive should read that as the price of no evaluator — and keep its accept/reject rule empirical while borrowing the pre-filter gate for efficiency.
3. **Design the composite-generation ledger around before/after snapshots per surface.** HANDOFF flags "lineage under multiple surfaces" as unresolved; prime-agent's `AppliedRefinementEdit {before?, after?, applied, error}` is a working schema for exactly that: per-surface deltas inside one journaled event, supporting partial-failure reporting and per-surface rollback.
4. **Keep the trust boundary in code, and keep secrets/host state behind a typed bridge.** Prime-agent's host-request pattern (evolvable/model-facing runtime can only reach trusted state via validated typed requests) is the architectural template for strive's sandbox boundary when strategies eventually get tools: the strategy process should reach the harness only through a narrow, validated request channel, never shared memory or ambient credentials.
5. **Concurrency will arrive with slow proposers — plan for it now in the interface.** Even single-machine strive will have seconds-long model calls between diagnose and accept. A `baseline` (incumbent generation id) parameter on `decide()` that rejects when the active generation moved is one line of interface today and prevents a class of races later.
6. **Adopt "self-modification only at cycle boundaries" as an explicit invariant.** Prime-agent's never-mid-cell rule maps to strive as: the evolvable surface is immutable within a cycle; activation happens only between cycles, and the post-activation environment is rebuilt (as prime-agent rebuilds the system prompt). Worth stating in the charter's trusted-surface section since it becomes non-obvious once cycles run concurrently.
7. **A refinement-history summary injected into the proposer's context is cheap compounding.** Prime-agent feeds the last 20 refinement results (with outcomes) back into every planning call so the model can see what was tried and roll back its own mistakes. Strive's ledger already contains this; formatting recent generations/decisions into the stage-2 proposer prompt is a low-cost way to get "learning from its own acceptance history," not just from execution traces.
