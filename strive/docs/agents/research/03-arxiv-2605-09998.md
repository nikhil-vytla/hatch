## Source-supported facts

**Context and lineage (§1, §4.2, App. B).** The paper first reports the authors' Gemini Plays Pokémon (GPP) project: with *human-in-the-loop* harness refinement (humans reading livestreamed trajectories and rewriting the harness), Gemini models became the first AI system to complete multiple Pokémon RPGs — Blue (May 2025), Yellow Legacy on hard mode (Aug 2025), Crystal without a lost end-game battle (Nov 2025). In later GPP runs the hand-authored specialist sub-agents were replaced with meta-tools (`define_agent`, `run_code`, notepad edits, custom tool creation) and the model built its own pathfinders, battle strategists, and reusable scripts unprompted (§4.2) — e.g., wrapping an `autopress_buttons` sandbox loophole into a general `press_sequence` primitive, and authoring a truth-table representation of a switch puzzle in its notepad.

**Harness formalization (§2.2).** A harness H has four components: system prompt `p`, sub-agents `G`, skills `K` (both text-level heuristics and executable programs), and memory `M`. Meta-tools let the model edit all four in place. Conditions: `H_min` (frames + ASCII text map + buttons + generic prompt, nothing else), `H_expert` (hand-engineered: A\* pathfinding, type chart, damage calculator, curated objectives, built sub-agents), and `H_CH` (starts from `H_min`, refines during play).

**Continual Harness method (§3.1–3.2).** Two loops within one continuous episode. Inner loop: model M wrapped by current harness H_t maps observation s_t = (frame o_t, text map m_t) to a button action. Outer loop: every `F` steps (after warm-up `W`), an LLM **Refiner** reads the recent trajectory window τ_{t−F:t} for failure signatures (navigation loops, tool-call failures, stalled objectives, missed exploration) and emits per-component edits Δ = (Δp, ΔG, ΔK, ΔM); H_{t+1} = H_t ⊕ Δ takes effect on the next step with no environment reset. `p` is rewritten wholesale conditioned on identified failures; `G`, `K`, `M` receive CRUD operations (create sub-agents for repeated multi-step patterns, delete unproductive ones; codify skills from successful sequences and repair code that raised exceptions; add/update/demote memory entries). Agent and Refiner are the *same model* invoked in different roles on different trajectory context, through the same meta-tool API. Refinement information accumulates monotonically over the episode; the paper argues reset-based optimizers (GEPA, MIPRO) structurally cannot reach failure modes that appear only deep in an episode (§3.2).

**Co-learning loop (§3.3, §4.5, App. D).** For open-source models: each iteration is a K=256-step DAgger rollout of policy π_θk inside the live-refining harness; a pairwise process reward model (Gemini-3-flash-preview) scores each transition over a sliding window (reward weights: trajectory progress 0.4, action correctness 0.3, reasoning quality 0.2, format compliance 0.1; stride 8); low-reward windows are relabeled by a Gemini-3.1-pro frontier teacher; a soft SFT update (3 epochs, lr 5e-6) produces θ_{k+1}. Reset-free: the saved emulator state at end of iteration k is loaded as the start of k+1. Warm-up: LoRA SFT (r=256, α=256, lr 2e-5, 8K context) on frontier CH trajectories, then offline GRPO (G=4 candidates/state, oracle-scored on action correctness 0.6 + format 0.4, lr 1e-6, KL β=0.04, 590 steps). Neither warm-up stage alone produces milestone advancement (Table 5, App. D.2); live gains begin only at the co-learning stage.

**Benchmarks and headline numbers (§4.1, §4.3–4.4, App. A).** Environments: Pokémon Red (18 canonical milestones through 3rd gym) and Emerald (31 milestones), using the PokeAgent Challenge standardized milestone evaluation; primary metric is *cumulative button presses to milestone* (a press_buttons call emitting [A, A, DOWN] counts 3). ≥3 seeds everywhere, seed medians reported. Results:
- CH substantially reduces button-press cost vs `H_min` on both games and "recovers a majority of the `H_min`-to-expert efficiency gap" with no curated knowledge, tools, or scaffolding (§4.3). Residual gap concentrates in dialogue-heavy gym interiors and multi-turn battle strategy.
- Capability dependence (§4.4, Emerald cost–completion Pareto): on Gemini 3.1 **Pro**, from-scratch CH reaches 100% of milestones at $130 median API spend vs `H_min` 98% at $215 (~40% cost cut, strictly Pareto-dominant); bootstrap variants 96–100% at $110–140. On **Flash**, high variance; bootstrap-updating 80% at $42 vs `H_min` 77% at $30. On **Flash-Lite**, `H_min` gets 20% at $11 while *every* CH variant falls to 3–13% at comparable or higher cost — a capability floor below which refinement cannot bootstrap (§6).
- Bootstrap variants (§4.1): *bootstrap-frozen* loads a successful from-scratch run's final harness with refinement disabled; *bootstrap-updating* loads it and keeps refining. On Red, bootstrap-updating beats from-scratch at every milestone — refined harness state transfers across runs even when game state resets (§4.3).
- Skill self-improvement toward an oracle (§4.6, App. C.1.1): navigation skills scored against a Dijkstra/BFS oracle; from-scratch path-cost deficit falls from ~50% penalty to single digits early in a 24-hour run and stays there; repairs happen in-episode ("failures from earlier invocations are diagnosed by the Refiner and the affected skills are repaired before later invocations within the same episode").
- Co-learning (§4.5, Fig. 7, App. D.4): Gemma-4 advances in-game milestones across training iterations from both beginning-of-game and mid-game checkpoints, reset-free; advances are bursty, preceded by sustained PRM reward ≥~0.40. Negative control: Qwen3.5 (27B/35B) without warm-up emits parseable tool calls but never leaves the starting area.

**Ablations / mechanism attribution (App. C).**
- *Skills* absorb most of the `H_min`→CH delta (C.1.1); the refined library is heavily biased toward BFS/A\* wrappers because navigation savings are the strongest local signal.
- *Skill debugging* (C.1.2): a create-and-forget funnel — most authored skills are never invoked; a small working set absorbs the bulk of calls; the loop "triages: it repairs the skills the agent depends on, tolerates regressions on unused ones."
- *Sub-agent handoffs* (C.1.3): sub-agent per-step token cost sits ~an order of magnitude below the orchestrator's; clean-return and on-task-recovery rates are near the top of the scale for navigation/dialogue/menu tasks. "The harness rather than the raw model carries most of the long-horizon performance."
- *Memory reuse* (C.1.4): every step prompt lists all memory IDs/titles ("LONG-TERM MEMORY OVERVIEW"); pull rate is honest-low — from-scratch runs write many entries and rarely read them back; bootstrap runs consult inherited memory actively at bottlenecks. "The transferable unit of the framework is therefore the harness across runs, not a single episode."
- *Bootstrap transfer* (C.2, Table 2): inherited-component usage is ~100% on Emerald for all stores; on Red, inherited sub-agent share collapses to 6.4%±5.7 under bootstrap-updating, and the milestone staircase regresses below even `H_min` "in lockstep with the collapse of sub-agent use" (C.2.1): newly authored sub-agents overtake inherited ones around step 213 without having gone through the repair cycle. Proposed fixes: a reuse prior on selection, or a deletion rule deprecating new sub-agents whose task signature is covered by inherited ones.

**Failure case study (App. B.3, Power Plant Route Loop).** A 1,003-turn (~3.5 h) stall: the agent deleted a working tool, authored `fly_menu_navigator`, then violated the meta-harness execution schema (needed `buttons_to_press: ["tool"]`, sent `["Down"]`), repeated the identical payload 842 times while its reasoning log claimed the tool was working, and escaped only when the menu cursor wrapped around. Observations recorded: tool generation happens in the first 50–200 turns of a bottleneck and *ceases beyond ~500 turns of stall*; persistent-memory rules do not prevent schema mismatch; assumed-tool-success caused prolonged feedback blindness.

## Deep dive — the nine special questions

**1. Reset-free online adaptation.** The paper's central claim. Adaptation happens *within a single continuous episode*: the Refiner edits the live harness every F steps and the agent keeps playing; no environment reset occurs at either the inference level or (in co-learning) the training level, where emulator state persists across training iterations (§3.1–3.3). Explicitly contrasted with GEPA/MIPRO-style prompt optimization, which "run complete episodes and reset between updates" (§1, §3.1). The authors argue reset-free is "the practically dominant regime for long-running coding agents, embodied agents, and ops tasks where free environment resets are costly or unavailable" (§3.2). A head-to-head reset-free vs batch-with-resets comparison on the same task is explicitly left open (§6).

**2. Alternating acting and refinement phases.** Formal two-loop architecture (§3.1, Fig. 2a): inner loop = act (model + current harness → button per step); outer loop = refine (every F steps after warm-up W, Refiner reads the window τ_{t−F:t}, runs **four passes** — prompt, sub-agents, skills, memory — and applies Δ). The alternation is time-triggered (cadence F), not event-triggered. Agent and Refiner share the same underlying model and the same meta-tool edit API; "they differ only in when each is invoked and on what trajectory context." The same alternation is claimed to run at two timescales: harness edits at inference, weight updates across training iterations (§6).

**3. Learning from continuing trajectories (no episode boundaries).** Yes, by construction. Refinement conditions on "any past trajectory data" collected "so far in the episode" (abstract, §3.1); failure signatures observed early "remain available to all subsequent refinement passes, so refinement quality compounds with episode length" (§3.2). The key claimed advantage over episodic methods: reaching failure modes that only manifest deep in a run (late-game battles, multi-step puzzles, dialogue chains). Concretely evidenced by in-episode skill repair (§4.6, C.1.2: "the failure record and the repair sit inside the same trajectory, so the loop closes within a run rather than across resets"). In co-learning, "each curve is a single agent's in-game trajectory traversed across its own training, not an aggregate over independent rollouts" (§4.5).

**4. Which surfaces are adapted.** Exactly four, all declared: **system prompt** (wholesale rewrite conditioned on failures), **sub-agents** (CRUD; created for repeated multi-step patterns, deleted when not invoked productively), **skills** (CRUD; both text heuristics and executable programs — codified from successful sequences, repaired when code raises exceptions), **memory** (CRUD; gap-filling, staleness updates, importance demotion) (§2.2, §3.2). The *edit mechanism* (meta-tool API: `define_agent`, `run_code`, `process_memory`), the environment interface, the Refiner itself, its cadence, and the evaluation are all fixed. Model weights are additionally adapted only in the co-learning extension (§3.3).

**5. Long-horizon and partially observable environments.** The target domain. Pokémon RPGs are explicitly framed as "long-horizon partial-observability decision-making" (abstract): tens-of-hours runs (24-hour Emerald seeds; the Yellow Legacy GPP run spans >160k turns per checkpoint labels), gated objectives, backtracking, nonlinear dependencies (App. A). Partial observability is explicit: the agent sees only frame + local ASCII map ("no NPC intent or battle mechanics beyond what the frame and map expose," §2.1); the text map has "no walkthrough, no objective list, and no global map information beyond what is currently visible" (App. A). Sub-agent context partitioning (C.1.3) is presented as what makes long horizons tractable: cheap specialized contexts plus trusted returns.

**6. How progress is measured without simple resets.** Multiple instruments, all applicable mid-run: (a) a **dense canonical milestone sequence** (PokeAgent Challenge) reached "roughly monotonically," with **cumulative button presses to milestone** as the primary cost metric (App. A) — cost-normalized progress rather than episodic return; (b) a **cost–completion Pareto plane** using real API spend (§4.4); (c) **oracle-relative skill scoring**: navigation skills scored against Dijkstra/BFS-optimal path cost per first-traversal segment, filtering out dialogue/battle presses — "a direct measure of skill self-improvement, independent of end-task efficiency" (§4.6, C.1.1); (d) **per-skill rolling success rate** in windows before/after each update (C.1.2); (e) **handoff exit/focus rates** for sub-agents (C.1.3); (f) **memory pull rate** localized to bottleneck windows (C.1.4); (g) in training, a **process reward model** scoring every transition (§3.3). Notable: harness *quality* during GPP is "established separately by GPP's completion record" (§4.2) — i.e., no per-edit acceptance test exists; measurement is diagnostic, not gating.

**7. Resistance to myopic recent-experience updates (recency bias / catastrophic drift).** The weakest part of the design, and the paper is candid about it. Mitigations that exist: monotone accumulation of failure signatures across the whole episode (§3.2); memory-staleness updates and importance demotion (§3.2); deletion of unproductively-invoked sub-agents; triage behavior that concentrates repair on the actually-used working set (C.1.2). But there is **no acceptance gate**: Refiner edits apply immediately without validation against any held-out check, and the documented **Red bootstrap-updating regression** (C.2.1) is a real catastrophic-drift event — the agent abandons a proven inherited sub-agent library (inherited share 6.4%) for fresh unrepaired ones and regresses below the minimalist baseline. The prompt "cycles between growth and simplification" and undergoes periodic full structural rewrites (§4.2, Fig. 4) with no rollback mechanism. The Power Plant loop (B.3) shows a complementary failure: *insufficient* updating under a long stall (tool creation ceases past ~500 stalled turns; feedback blindness). Proposed but unimplemented remedies: reuse priors, coverage-based deletion rules (C.2.1), "an explicit reuse prior is a natural next step" (C.1.4).

**8. Transfer to coding, research, and tool-using agents.** Claimed as motivation, not demonstrated. The paper positions itself as building "what Claude Code/OpenHands/OpenClaw are for coding" for embodied agents (§1), and asserts reset-free is the dominant regime "for long-running coding agents, embodied agents, and ops tasks" (§3.2). All experiments are on Pokémon. The harness decomposition (prompt/sub-agents/skills/memory), the CRUD-refiner pattern, oracle-relative skill scoring, and the bootstrap-transfer protocol are domain-general in form, but no coding/research benchmark is run. **Not empirically addressed by source** beyond the framing.

**9. Boundary between harness learning and model-weight learning.** Explicitly architected as two coupled timescales (§3.3, §6): harness state H_t updates *within* an iteration via in-context Refiner edits; weights θ update *across* iterations via soft SFT on teacher-relabeled low-reward windows. The trajectory distribution depends on θ *through* the harness ("the model's actions induce τ, the Refiner reads τ to update H_t, and H_t in turn shapes the next observation distribution"). Boundary findings: (a) a **capability floor** — below some model capability (Flash-Lite), harness learning is net-negative because the model cannot exploit the components (§4.4, §6); (b) harness gain **scales with capability** (Pareto-dominant only on Pro); (c) weight learning alone (SFT + offline GRPO) yields *zero* milestone progress — only the joint loop moves the agent (§4.5, Table 5); (d) the current instantiation needs a *frontier teacher* distinct from the student; same-model teacher/trainee "extends" the framework but ≤31B open models aren't capable enough (§6).

## Analysis dimensions

- **Runtime, task, environment, and state models.** Emulated Game Boy/GBA RPGs stepped 120 frames per decision; observation = upscaled screen frame + ASCII tile map (derived from emulator RAM but restricted to screen-visible information); action space = 8 buttons; a memory reader exposes structured RAM state only to expert-harness tools and text-map derivation (App. A). Environment state is fully persistent (savestates carried across training iterations). Task model = canonical milestone sequences with button-press cost.
- **Observation, trajectories, traces, memory, persistence.** The full episode trajectory τ is retained and is the Refiner's evidence base; refinement conditions on windows τ_{t−F:t} but signatures accumulate episode-long (§3.2). Memory M is a persistent keyed store; every step prompt carries a catalog of memory IDs/titles, with content fetched on demand via `process_memory` (C.1.4). Harness state (skills/sub-agents/memory files, e.g. `custom_agents.json`, App. B.1) persists across runs and is the bootstrap-transfer artifact.
- **Trusted/immutable vs evolvable surfaces.** Evolvable: p, G, K, M. Trusted/fixed: environment interface, meta-tool API and its execution schema, Refiner logic and cadence, milestone evaluation, PRM and teacher. The boundary is implicit in the architecture rather than stated as a safety principle; notably the *executable* skills run through `run_code` with at least one documented sandbox loophole the agent exploited (`autopress_buttons`, §4.2). No discussion of protecting the evaluator from the loop.
- **Recursive decomposition, subagents, context management.** Core mechanism: orchestrator delegates to self-authored sub-agents with narrow specialized contexts; sub-agent token cost ~10× below orchestrator; explicit `return_to_orchestrator` handoff with measured exit/focus quality (C.1.3). One level of delegation (orchestrator → sub-agent); no deeper recursion described. Context growth is managed by delegation + memory catalog + prompt rewrites; the paper cites recursive-LM work but describes itself as "structured edits… at depth 1" (§5.3).
- **Candidate generation and self-modification.** Generation = LLM Refiner emitting CRUD edits from failure signatures; also emergent agent-initiated self-modification through the same meta-tools during play (GPP). No population, no crossover, no sampling of multiple candidate harnesses; a single lineage per run.
- **Evaluation, selection, promotion, rollback, lineage.** The thinnest dimension. Edits are applied unconditionally — no candidate-vs-incumbent comparison, no acceptance rule, no promotion gate, no rollback. Selection pressure is only *behavioral* (unused components deleted; broken skills repaired after they fail in live use). Lineage exists as revision checkpoints of component files (14 battle-agent checkpoints extracted from `custom_agents.json`, App. B.1) — an audit trail, not a control mechanism. Bootstrap-frozen is the closest thing to pinning a validated artifact.
- **Sandboxing, secrets, permissions, budgets, recovery.** Largely not addressed by source. `run_code` executes agent-authored programs; the one "sandbox" mention is the agent *escaping* an intended restriction (`autopress_buttons` loophole) — celebrated as emergent skill-building rather than treated as a containment failure (§4.2). Budgets appear only as measurement (API spend on the Pareto plane, 24-hour wall-clock caps), not enforcement. Recovery from stalls is emergent and unreliable (B.3). No secrets/permissions model.
- **Online adaptation vs offline optimization.** Squarely online: mid-episode in-context adaptation, contrasted explicitly with offline/reset-based prompt optimizers (§3.1, §5.1). The co-learning pipeline layers offline warm-ups (SFT, offline GRPO) under an online loop, and shows the offline stages alone are behaviorally inert (Table 5).
- **Harness adaptation vs model-weight learning.** Both, deliberately separated by timescale and coupled through shared trajectory data; capability floor and teacher-dependence findings above (Deep dive #9).
- **Genuinely self-improving vs merely persistent/configurable.** The paper supplies unusually direct evidence of genuine self-improvement: oracle-relative skill quality improves in-loop (§4.6); skills are measurably repaired after in-episode failures (C.1.2); refined harness state transfers and accelerates fresh runs (§4.3, C.2). It equally documents the limits: most authored artifacts are create-and-forget; memory is written far more than read; improvement is unvalidated and can regress catastrophically (C.2.1).
- **Mechanisms suitable for a robust, long-lived harness.** Transferable: the four-surface decomposition with a uniform CRUD edit API; time-triggered refinement over trajectory windows with monotone failure-signature accumulation; oracle-relative per-component scoring; sub-agent context partitioning with measured handoff quality; bootstrap-frozen vs bootstrap-updating as a transfer/ablation protocol; provenance tagging of every invocation (inherited vs newly authored, Table 2). Missing for robustness: acceptance gating, rollback, reuse priors, stall detection.

## Interpretations

*The following are inferences by this reviewer, not claims of the paper.*

1. **Continual Harness is strive's complement, not its competitor.** strive's loop is *gated* (propose → validate → accept/reject with a journaled decision); CH's loop is *ungated* (refine → apply, quality enforced only by later behavioral triage). CH buys breadth (four surfaces, mid-episode speed) at the price of exactly the guarantees strive's charter demands. The Red bootstrap-updating regression is what strive's acceptance rule exists to prevent — and CH's authors independently arrive at strive-shaped fixes (reuse priors, deletion rules) after the fact.
2. **The absence of an acceptance gate is load-bearing, not incidental.** Mid-episode refinement cannot easily A/B a candidate harness against an incumbent because the environment is non-resettable and non-forkable in general. The paper's workaround — score components against *local oracles* (Dijkstra for pathfinding) and *rolling success rates* instead of end-task return — is the transferable idea: per-surface proxy validators that don't require resets.
3. **"The harness is the transferable unit" is the paper's most strive-relevant empirical claim.** Refined harness state (not the trajectory, not the weights) is what carries improvement across runs — which is precisely strive's ledger-of-generations bet, validated in a much harsher domain.
4. **The capability floor cuts both ways for strive.** CH shows harness self-improvement is worthless (net-negative) below a model-capability threshold. strive's deterministic-stub stages sidestep this, but the finding predicts that strive's stage-2 ModelProposer gains will be sharply model-dependent, and that a weak proposer should fail *safe* (rejected candidates) rather than fail *degraded* as CH does.
5. **The Power Plant loop is an argument for trusted-surface stall detection.** The agent's own reasoning was confidently wrong for 842 identical actions; only an environmental coincidence broke the loop. Self-diagnosis cannot be the sole stall detector; a trusted, dumb, mechanical monitor (identical-action counters, progress-metric flatlines) must live outside the evolvable surface.
6. **The recency-bias verdict:** CH mitigates myopia in *evidence* (monotone signature accumulation) but not in *action* (unvalidated immediate edits, wholesale prompt rewrites). Its two documented pathologies are the two poles strive should test for: over-updating (discarding proven components) and under-updating (frozen repetition under stall).

## Hypotheses to test in strive

1. **Gated vs ungated refinement:** on a multi-cycle task stream, an ungated CH-style refiner improves faster early but suffers regressions that a strive-style accept/reject gate prevents; net long-run performance favors gating. (Directly testable once strive has ≥2 tasks and a model proposer.)
2. **Inheritance protection:** if candidate artifacts must beat the *inherited* incumbent on the incumbent's own invocation distribution before replacing it, the Red-style bootstrap regression (new unproven sub-agents displacing proven ones) does not occur.
3. **Per-surface proxy validators:** validating a component against a local oracle/rolling-success proxy (CH §4.6 style) approximates full end-task validation at a fraction of the cost — test whether proxy-gated acceptance correlates with full-suite-gated acceptance on strive tasks.
4. **Create-and-forget economics:** most generated artifacts will never be invoked; a periodic reaper (delete never-invoked artifacts after N cycles) reduces context/ledger cost with no performance loss.
5. **Write-vs-read memory asymmetry:** a memory surface without an explicit reuse prior (catalog injection + retrieval nudge) will be written but not read; measure pull rate as CH does before trusting memory as an evolvable surface.
6. **Stall detection as trusted surface:** a mechanical repeated-outcome detector (k identical failing actions / flat eval score over m cycles) catches stalls that trace-reading diagnosis misses; CH's 500-turn tool-creation horizon predicts self-diagnosis degrades exactly when it is most needed.
7. **Time-triggered vs event-triggered refinement:** CH refines every F steps regardless of need; strive diagnoses on failure evidence. Test whether cadence-triggered proposal cycles find improvements that failure-triggered ones miss (e.g., efficiency wins on passing tasks).

## Mechanisms: early prototype vs mature harness

**Early prototype (adoptable at strive's current stage):**
- Provenance tagging on every artifact invocation — *inherited vs authored-this-run* — is a one-field ledger addition that made CH's most important failure diagnosable (Table 2). strive's ledger already has lineage; add *usage* accounting.
- Rolling per-artifact success-rate accounting (invocations before/after each change, C.1.2) — cheap, derivable from strive's existing trace events.
- Bootstrap-frozen vs bootstrap-updating as a standing experiment protocol for "does refinement still add value on top of an inherited harness?" — maps directly onto strive's activation pointer (activate an ancestor with the loop disabled vs enabled).
- Mechanical stall detector on the trusted surface.
- The failure-signature taxonomy (navigation loops → task loops; tool-call failures; stalled objectives; missed opportunities) as seed signatures for strive's diagnosis registry beyond the single planted one.

**Mature harness (stage 3–5 of strive's roadmap):**
- The four-surface decomposition (prompt/sub-agents/skills/memory) with one uniform CRUD edit API and per-surface rollback — CH demonstrates the composite-generation problem strive's HANDOFF already flags (one artifact per generation won't survive multi-surface evolution).
- Mid-episode/mid-run refinement without resets — relevant once strive tackles long-horizon agentic tasks (stage 4–5) where re-running the full eval suite per candidate is unaffordable; requires the proxy-validator machinery first.
- Per-surface oracle scoring (skills vs a computable optimum) as risk-scaled validation — matches the charter's "validation effort scales with the risk of the change."
- Model–harness co-learning (PRM scoring + teacher relabeling + weight updates) — explicitly outside strive's charter (no model-weight training) but defines what sits on the far side of strive's boundary; the finding that harness-only and weights-only each fail alone is the strongest available argument that the boundary is a real design object.
- Sub-agent delegation with measured handoff quality (exit/focus rates) — the observability pattern to copy when strive reaches recursive delegation (stage 5).

## Implications for strive — concrete interface/design consequences

1. **Keep the acceptance gate; make it inheritance-aware.** `decide` should distinguish *replacing a proven incumbent* (require evidence on the incumbent's historical invocation profile) from *adding a new artifact* (cheaper bar). This is the direct lesson of C.2.1 and is expressible now as a rule parameter, before any model proposer exists.
2. **Add usage accounting to the ledger.** Extend trace/ledger events so every strategy (later: every artifact) invocation records which generation served it. CH's Table 2 shows inherited-share is the single best early-warning signal for drift; strive can compute it for free from the ledger if invocations are journaled.
3. **Plan the composite-generation schema around four named surfaces.** CH's (p, G, K, M) with per-surface CRUD deltas is a concrete, evidence-backed target for strive's stage-3 "lineage under multiple surfaces" problem: a generation becomes a set of per-surface deltas over a parent, each independently activatable/rollback-able — CH lacks the rollback half; strive should not.
4. **Introduce a `Validator` notion parallel to `Proposer`.** CH shows full end-task validation is sometimes impossible (no resets) and per-surface proxies (oracle path cost, rolling success) are viable substitutes. strive's stage-2 redesign should make validation pluggable per surface/risk tier, not hard-code "run the case suite" — the case suite becomes one Validator among several.
5. **Put stall detection on the trusted surface now.** A cycle-level monotone-progress monitor (same evaluation score + same diagnosis N cycles running → flag/halt/escalate) is cheap at v0 scale and addresses the failure class (B.3) that evidence-driven diagnosis is structurally blind to: confidently-wrong self-models.
6. **Treat memory as a surface that must earn its keep.** When memory becomes evolvable (stage 5), instrument pull rate from day one and require demonstrated reads before counting memory changes as improvements; otherwise acceptance rules will happily accrete write-only state, per C.1.4.
7. **Expect and design for capability-dependent gains.** Stage-2 acceptance statistics should be reported per proposer model; the CH Flash-Lite result predicts that below some capability the correct system behavior is a high rejection rate (safe stagnation), and a *rising acceptance rate with a falling held-out score* is the signature of the dangerous regime.
8. **Sandbox lesson:** CH's agent exploited a harness loophole and the meta-harness silently ignored malformed tool calls (B.3). strive's runner should *reject loudly* on schema mismatch (an observable failure event) rather than fall through to a default behavior — silent fallback is what turned one bad call into an 842-repetition loop.
