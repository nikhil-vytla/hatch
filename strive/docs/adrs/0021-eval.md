# ADR-0021: `strive eval`, whether learning helps

Status: proposed. Nothing here is built; the questions at the end need an
answer before it is.

## Context

strive learns by proposing changes to memory and skills that a person
accepts. Nothing yet measures whether an accepted change helps. The
per-proposal replay check that tried to (ADR-0018, superseded) had no
power: at 3 runs a side, a change that does nothing passes "with more than
without" about a third of the time.

What the rest of the field does (NOTES, 2026-09-28):
- **Prime Agent** gates releases with an A/B run: 28 fixed, stratified
  tasks, one pinned model, a gold-patch oracle that must pass first, no
  retries, fail-closed thresholds. It never measures its own refinement.
- **exo** runs Harbor trials in order on one evolving agent, against plain
  control harnesses. It doesn't yet measure its learning step either.
- **Research** says the answer may be "barely". Self-written skills scored
  −1.3 points (SkillsBench); four production memory systems failed to beat
  memory-off in 11 of 12 pairings (VibeMemBench). A harness update helps a
  weak model far more than a strong one (2605.30621).

So the question to answer first is the plain one: **does strive with
learning on do better, over a sequence of related tasks, than the same
strive with learning frozen?**

## Decision

### What is compared

Two arms, run on the same ordered task sequence with the same pinned model:
- **frozen:** memory and skills as they were at the start; the learner
  never runs.
- **learning:** after each task, the learner runs on that task's session,
  and every proposal that passes the static check is accepted. The eval
  stands in for the person. The judge's advice is recorded, not obeyed.
  A second variant, accepting only what the judge passes, is optional.

Learning can only help if later tasks resemble earlier ones. So a sequence
is **one project and one task family repeated with variation**, not a
general benchmark of unrelated containers. Terminal-Bench measures the
agent, not project memory.

### The task set

A small, versioned local suite under `eval/`, of task families, each with a
checkable outcome:
- The suite starts from strive's own history: tasks mined from this
  repository's sessions and commits with a test that goes red to green. It
  can then add one public continual set if one exists by then
  (SWE-Bench-CL, VibeMemBench).
- Each task has an **oracle**: a known solution that passes its check. The
  eval runs the oracle first and refuses to score a task whose oracle
  fails.
- Tasks run through Harbor, reusing `harbor/strive_agent.py`. Trials in a
  sequence run one at a time and carry `.strive/` forward between them;
  the frozen arm resets it each time.

### How it's scored

- **Paired by task:** each task has a frozen and a learning result, so
  the comparison is McNemar's test on the tasks where the arms disagree,
  not two independent pass rates.
- **Power stated up front.** Detecting a 10-point lift at α 0.05 and power
  0.8 takes roughly 120 to 230 paired tasks; a 20-point lift, about 40.
  A run reports what it can and can't detect.
- **Reported:** pass rate per arm with Wilson intervals, the paired
  difference and its p-value, cost and turns per task, and for the
  learning arm, whether each later session loaded the learned files and
  whether a lesson's cited failure came back.
- **Fail-closed:** a missing trial, a failed oracle or a model change
  fails the run rather than scoring around it. No retries.
- Scored from artifacts (exit codes, check results), never from what the
  agent says about itself.

### Where it lives

A script first (`scripts/eval/`), not a `strive eval` command: it's for
people deciding what to build, and the command can come if it earns one.
It is run by hand or on a label, never on every PR.

## Consequences

- Learning features wait on this. If the learning arm doesn't beat the
  frozen one, the learning loop is simplified further, not extended.
- It costs real money on every run, so each run has a budget and a dry run
  that prints the plan and its estimated cost.
- A negative result is a result: it goes in NOTES with its numbers.

## Questions to settle before building

1. **Budget.** A pilot of about 40 tasks in 2 arms on Haiku 4.5 is roughly
   $5–15 and detects only large effects. A powered run of about 150 tasks
   is roughly $30–70 on Haiku, several times that on a stronger model.
2. **Model.** Haiku first: cheap, and the model that learning is most
   likely to help.
3. **Task source.** strive's own history first, or build a small synthetic
   task family (for example, a project with a quirky test command and
   conventions a first session gets wrong)?
